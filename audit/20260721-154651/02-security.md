This is a genuine new detective signal at the highest-risk surface (the public endpoint), which is why SEC-10 was upgraded from Missing to Partial this run.
- `aws_cloudfront_distribution.webhook` in front of the existing `aws_apigatewayv2_api.webhook`, with caching explicitly disabled (`Managed-CachingDisabled`) and all headers/body forwarded unmodified (`Managed-AllViewerExceptHostHeader`) so the GitHub HMAC signature (computed over the raw body) still validates correctly through the proxy — _evidence: `documentation/terraform/ingestion/waf.tf:134-176`_. `web_acl_id` correctly uses the WAFv2 **ARN** (a common Terraform footgun for CloudFront associations) — _evidence: `documentation/terraform/ingestion/waf.tf:139`_.
- CloudFront-in-front-of-an-HTTP-API is the AWS-documented workaround for the fact that WAFv2 cannot attach directly to `aws_apigatewayv2_api` (only REST APIs, ALB, CloudFront, AppSync, Cognito, App Runner, Amplify are supported WAF targets); this is not an architectural smell.
- `outputs.tf` was updated so the "official" webhook URL routes through CloudFront (`webhook_url`), with a separate, explicitly-labeled `webhook_api_gateway_url` output documented as "debug/diagnostic uniquement... contourne le WAF" — _evidence: `documentation/terraform/ingestion/outputs.tf:1-9`_.

**Residual gap, independently confirmed by reading `main.tf` and `handler.py` directly:** the raw `aws_apigatewayv2_api.webhook.api_endpoint` (`execute-api...amazonaws.com`) is still directly reachable. Nothing added by this fix rejects direct-origin traffic — no API Gateway resource policy, no shared-secret/custom-header check in the Lambda comparing an `X-Origin-Verify`-style header set only by CloudFront. `handler.py`'s only gate is the HMAC signature check (`documentation/scripts/lambdas/webhook-receiver/handler.py:217-226`), which is invoked identically regardless of which URL the request arrived on — it has no awareness of whether the request transited CloudFront/WAF or hit the origin directly. This is explicitly acknowledged in a code comment in the new file itself (`documentation/terraform/ingestion/waf.tf:18-21`, calling it a known, out-of-scope limitation).

Assessed impact of the residual gap: **Low, not Medium** (downgraded from the prior finding's Medium rating, reflecting that the primary risk — an unauthenticated write path — never existed and still doesn't). Two structural facts bound the risk: (1) API Gateway stage-level throttling (`throttling_burst_limit=20`, `throttling_rate_limit=10`, `documentation/terraform/ingestion/main.tf:257-260`) applies to all requests reaching the `$default` stage regardless of entry path (direct or via CloudFront), so the account-wide rate ceiling is not bypassed — only the WAF's own 2000/5min-per-IP rule and the managed rule sets are bypassed. (2) The Lambda performs no rendering/SQL/shell execution reachable pre-HMAC, so AWSManagedRulesCommonRuleSet/KnownBadInputsRuleSet (aimed at XSS/SQLi/LFI-style payloads in traditional web apps) have limited marginal value for this specific JSON-only, HMAC-gated endpoint. Net effect: a bypass loses WAF's L7 pattern-matching and its per-IP rate rule, but not the two controls that actually gate write access (HMAC auth) or the two controls that bound cost/volumetric abuse (API GW account throttle, cheap-and-fast 401 rejection path). This is a real but narrow, already-documented residual gap, not a new exploitable hole — it is tracked below as a continuation of SEC-F1 (retitled), downgraded from Medium to Low.

## Weaknesses / Findings

### [Low] SEC-F1 — WAF/CloudFront front now in place, but the raw API Gateway origin remains directly reachable (residual bypass)
- **Evidence:** `documentation/terraform/ingestion/waf.tf:18-21` (comment acknowledging the gap); `documentation/terraform/ingestion/outputs.tf:6-8` (`webhook_api_gateway_url`, documented as bypassing the WAF); `documentation/terraform/ingestion/main.tf:234-269` (no resource policy or origin-verification mechanism on `aws_apigatewayv2_api.webhook`); `documentation/scripts/lambdas/webhook-receiver/handler.py:217-226` (HMAC check has no path/origin awareness).
- **Impact:** Traffic sent directly to the `execute-api` URL skips AWS Managed Rules and the WAF's per-IP rate rule, though it is still bound by API Gateway's account-wide stage throttle (10 rps / 20 burst, `documentation/terraform/ingestion/main.tf:257-260`) and still must pass the HMAC check before any state-changing action occurs. No unauthenticated write path exists via either route.
- **Recommendation:** Add a shared-secret custom header (e.g. `X-Origin-Verify`) set only by the CloudFront distribution's origin custom headers and checked in the Lambda before HMAC verification, so the raw API Gateway origin rejects direct traffic with a cheap 403 — closing the bypass without touching the HMAC logic itself.
- **Alternative solution:** (a) CloudFront custom-header origin-verification (recommended): pros — closes the bypass at negligible cost/complexity, standard AWS pattern for "CloudFront-only origin"; cons — one more secret/config value to rotate and keep in sync between CloudFront and the Lambda. Effort: S. (b) Do nothing further, treat as accepted residual risk (current state): pros — no additional work; cons — WAF's managed rule sets and rate limiting can be silently bypassed by anyone who discovers/enumerates the `execute-api` hostname (regional API Gateway domains are guessable-ish and sometimes indexed by scanners). Effort: none. Cross-pillar impact: none material (Cost Optimization: negligible; Reliability: none, throttle still applies either way).

### [Low] SEC-F2 — No customer-managed KMS keys (CMK); blocked at the account level
- **Evidence:** `documentation/terraform/security/main.tf:8-13,23,42` ("CMK KMS retirée : le rôle NewSysOps a un DENY explicite sur `kms:CreateKey`"), `documentation/terraform/ingestion/main.tf:104,150`, `documentation/terraform/roles/main.tf:77-78`.
- **Impact:** Every data store uses AWS-managed/owned keys rather than a project-scoped CMK: no customer-controlled key policy, no configurable rotation cadence, coarser CloudTrail key-usage attribution. Documented in-repo as a deliberate, account-policy-driven POC compromise, unchanged since the prior run.
- **Recommendation:** Request the narrow `kms:CreateKey`/key-management permissions needed (or have the account's security team provision a project CMK), then re-enable `kms_key_id` on Secrets Manager/DynamoDB/S3 and enable automatic key rotation.
- **Alternative solution:** Current AWS-managed keys vs. a project CMK. Pros of CMK: key-policy control, configurable rotation, cross-account boundary, fine-grained CloudTrail key-usage logs. Cons: added operational overhead/cost, currently blocked by an org-level IAM deny outside this project's control. Effort: M (dependent on an org-level permissions change).

### [Medium] SEC-F3 — No account/project-level detective controls (CloudTrail, Config, GuardDuty, Security Hub)
- **Evidence:** repo-wide grep across `documentation/terraform/` for `cloudtrail|aws_config|guardduty|securityhub` returns no matches; `documentation/terraform/observability/main.tf:1-169` defines only operational CloudWatch alarms/dashboard (DLQ depth, Lambda error counts), not security event detection; no `access_log_settings` on the API Gateway stage in `documentation/terraform/ingestion/main.tf:252-261`. The new WAF logging (`documentation/terraform/ingestion/waf.tf:128-132`) is a genuine but narrow improvement scoped only to the webhook edge, not an account-wide control.
- **Impact:** No centralized, immutable audit trail of API/IAM activity and no continuous threat/posture detection outside the webhook's own WAF logs. An IAM policy change, unusual `secretsmanager:GetSecretValue` pattern, or anomalous `bedrock-agentcore:InvokeAgentRuntime` call would not be independently detected.
- **Recommendation:** Enable an account/org CloudTrail trail and CloudWatch Logs metric filters/alarms on IAM policy changes and unusual Secrets Manager access; consider GuardDuty for lightweight always-on threat detection given this is a POC-scale account.
- **Alternative solution:** None — a baseline CloudTrail trail is a foundational, low-cost AWS control with no reasonable justification to omit even at POC scale. Effort: S.

### [Low] SEC-F4 — Bedrock model-invoke permission scoped wider than the models actually used
- **Evidence:** `documentation/terraform/roles/main.tf:42-49` (`Resource = ["arn:aws:bedrock:*::foundation-model/*", "arn:aws:bedrock:*:${account_id}:inference-profile/*"]`).
- **Impact:** The runtime execution role can invoke any foundation model in any region, not just the two Claude models actually configured. No direct exploit path identified; unnecessary blast-radius given the role's other permissions are tightly scoped.
- **Recommendation:** Scope the `BedrockInvoke` statement's `Resource` to the specific model/inference-profile ARNs and region (`eu-central-1`) actually used.
- **Alternative solution:** None needed — straightforward tightening consistent with the existing least-privilege pattern already applied elsewhere in this module. Effort: S.

### [Low] SEC-F5 — Unpinned Python dependencies, no lockfile
- **Evidence:** `documentation/scripts/agents/agent-technical-doc/requirements.txt:1-8` (`bedrock-agentcore>=0.1.0`, `strands-agents[otel]>=0.1.0`, `boto3>=1.34.0`, `botocore>=1.34.0`, `pyjwt[crypto]>=2.8.0`, `aws-opentelemetry-distro>=0.10.0`); no lockfile found in the repo.
- **Impact:** Container builds are not reproducible and can silently pick up new — possibly vulnerable — dependency versions between builds.
- **Recommendation:** Pin exact versions (or generate a lockfile via `pip-compile`/`uv lock`) and add periodic scanning (`pip-audit`, Dependabot/Renovate for Python deps).
- **Alternative solution:** None needed. Effort: S.
