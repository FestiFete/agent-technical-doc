## Charter & scope
This pillar assesses the workload's ability to perform its function correctly and consistently, and to recover from failures: fault tolerance and redundancy, recovery objectives (RTO/RPO) and backup strategy, retries/idempotency for at-least-once operations, dead-letter/failure isolation, graceful degradation, health-check-driven recovery, quota/throttling handling, safe change management, durable state, and failure-mode testing.

**Does NOT cover** (cross-referenced elsewhere): handling load growth / elasticity → Scalability (11); throughput/latency efficiency → Performance Efficiency (04); deploy-pipeline mechanics → Operational Excellence (01) (this pillar only covers change-safety *outcomes* — rollback, canary, reversible migrations).

## Strengths
- Strong idempotency design: DynamoDB conditional `PutItem` on `repo#pr#sha` for the agent run, and a separate conditional claim on `repo#pr#comment_id` in the webhook to deduplicate GitHub redeliveries; the claim is explicitly released only on failure so a manual re-run is possible, while success permanently blocks reprocessing of the same commit — _evidence: `documentation/scripts/agents/agent-technical-doc/docagent/idempotency.py:22-74`, `documentation/scripts/lambdas/webhook-receiver/handler.py:140-163,243-247`_
- Writes to GitHub (blob/tree/commit/comment) are deliberately **not** retried to avoid duplicate commits/comments, while GET reads are safely retried — a correct idempotency-aware retry boundary — _evidence: `documentation/scripts/agents/agent-technical-doc/docagent/github_client.py:88-99`_
- SQS main queue + DLQ with bounded `maxReceiveCount`, visibility timeout deliberately set ≥ worker timeout, and a dedicated `dlq_not_empty` alarm — async failures are isolated per-message instead of blocking the queue — _evidence: `documentation/terraform/ingestion/main.tf:6-23`, `documentation/terraform/observability/main.tf:24-38`_
- Explicit client-side timeouts on both external dependencies (Bedrock and GitHub) rather than relying on defaults — _evidence: `documentation/scripts/agents/agent-technical-doc/docagent/analyzer.py:176-178`, `documentation/scripts/agents/agent-technical-doc/docagent/github_client.py:63`_
- Transient-vs-permanent error classification with exponential backoff, exercised by dedicated unit tests (including a capped-backoff test) — _evidence: `documentation/scripts/agents/agent-technical-doc/docagent/retry.py:33-81`, `documentation/scripts/agents/agent-technical-doc/tests/test_retry.py:39-79`_
- All compute/data resources are fully-managed, inherently multi-AZ services (Lambda, SQS, DynamoDB PAY_PER_REQUEST, API Gateway HTTP API, Secrets Manager, Bedrock AgentCore Runtime) — no self-managed single-AZ instance is part of the design — _evidence: `documentation/terraform/ingestion/main.tf`, `documentation/terraform/security/main.tf:57-79`, `documentation/terraform/runtime/main.tf:3-44`_
- DynamoDB point-in-time recovery enabled; Terraform state bucket is versioned and KMS-encrypted — _evidence: `documentation/terraform/security/main.tf:74-76`, `documentation/terraform/bootstrap/main.tf:36-51`_
- Anti-DoS quota (`max_runs_per_repo`/`rate_window_seconds`) and bounded worker concurrency (`worker_max_concurrency`) show explicit awareness of downstream (Bedrock) throttling risk — _evidence: `documentation/scripts/lambdas/webhook-receiver/handler.py:184-213`, `documentation/terraform/ingestion/main.tf:226-228`, `documentation/terraform/ingestion/variables.tf:53-57`_

## Weaknesses / Findings

### [High] REL-F1 — No RTO/RPO defined and no cross-region DR strategy (mono-region)
- **Evidence:** All 7 Terraform modules' providers are pinned to a single region — `documentation/terraform/*/providers.tf` (e.g. `documentation/terraform/ingestion/providers.tf:17,24`), `documentation/terraform/shared.tfvars:14` (`aws_region = "eu-central-1"`). No `aws_dynamodb_table` global table, no cross-region replication anywhere in `documentation/terraform/`. Self-acknowledged gap: `documentation/AUDIT.md:82` ("mono-région / pas de DR"). No RTO/RPO figure found in `documentation/README.md`, `documentation/AUDIT.md`, or `.kiro/specs/agent-technical-doc/*.md`.
- **Impact:** A regional outage (or an availability-affecting incident scoped to `eu-central-1`) fully halts the ingestion→documentation pipeline with no defined recovery time or data-loss tolerance, and no tested failover procedure.
- **Recommendation:** At minimum, document an explicit RTO/RPO appropriate to this workload's criticality (it is a PR-comment-triggered async documentation generator, not a live user-facing system — POC framing may make a modest RTO/RPO acceptable). If the risk appetite requires more, add DynamoDB global tables for the idempotency table and a documented manual redeploy runbook to a second region for the stateless compute (Lambda/API GW/Bedrock AgentCore are all redeployable from Terraform + ECR).
- **Alternative solution:** (a) **Accept mono-region with a documented RTO/RPO** — lowest effort, appropriate given this is explicitly a POC per README/AUDIT.md; con: no protection against a regional event. (b) **Warm standby in a second region** (duplicate Terraform stack, DynamoDB global table, Route53/API-GW failover) — pros: bounded RTO; cons: roughly doubles infra cost and operational surface, requires CMK/cross-region KMS work already flagged as outstanding; effort L; cross-pillar impact: Cost Optimization (+infra spend), Operational Excellence (+deploy complexity), Security (cross-region KMS/IAM).

### [Medium] REL-F2 — No circuit breaking or graceful degradation on dependency failure
- **Evidence:** No circuit-breaker pattern found in `documentation/scripts/agents/agent-technical-doc/docagent/` (`grep -rli circuit` returns no matches). On GitHub/Bedrock failure, the only behaviors are: retry (`docagent/retry.py:53-81`), then fail the run and release the idempotency claim for a manual re-run (`docagent/idempotency.py:55-74`) — no fallback content, no fail-fast opening of a breaker after repeated failures to protect the downstream dependency or reduce wasted Bedrock spend during an outage.
- **Impact:** During a sustained GitHub or Bedrock outage, every queued/retried run continues to consume full retry budgets and Bedrock invocation attempts until SQS `maxReceiveCount` (2) is exhausted and the message lands in the DLQ — no early-exit behavior once the dependency is known to be down.
- **Recommendation:** Add a lightweight breaker (e.g., a DynamoDB/ElastiCache flag or a CloudWatch-alarm-driven Lambda concurrency throttle) that short-circuits new invocations for a cooldown window once the `runtime_errors_alarm` or GitHub 5xx rate crosses a threshold, posting a "temporarily unavailable, will retry later" PR comment instead of burning retries.
- **Alternative solution:** Given the workload is low-QPS and asynchronous (not user-facing/latency-sensitive), a simpler alternative is to keep retry+DLQ as-is and rely on the existing `dlq_not_empty`/`runtime_errors_alarm` alarms for human-driven mitigation; pros: zero added complexity; cons: no automatic cost/blast-radius containment during a sustained outage. Effort S (alarm-driven throttle) to M (full breaker). Cross-pillar impact: Cost Optimization (avoids wasted Bedrock spend during outages).

### [Medium] REL-F3 — CloudWatch alarms are defined but wired to no notification target by default
- **Evidence:** `alarm_actions` defaults to `[]` (`documentation/terraform/observability/variables.tf:21-25`) and is referenced unmodified by all four alarms (`documentation/terraform/observability/main.tf:24-70`, incl. `runtime_errors_alarm` at `documentation/terraform/runtime/logs.tf:79-94`). No `aws_sns_topic` (or any other alarm-action target) resource exists anywhere under `documentation/terraform/` (repo-wide search returns none), and no override is set in `documentation/terraform/shared.tfvars` or any committed `terraform.tfvars`.
- **Impact:** `dlq_not_empty`, `worker_errors`, `webhook_errors`, and `runtime_errors_alarm` will all transition to ALARM state on failure but, unless an operator manually passes `-var alarm_actions=[...]` at apply time (undocumented in README), nobody is notified — failures are only visible by proactively opening the CloudWatch dashboard.
- **Recommendation:** Add an `aws_sns_topic` (+ email/Slack/chat-ops subscription) to the `observability` module and default `alarm_actions` to it, or document the required `-var` override explicitly in the README runbook.
- **Alternative solution:** None — this is a low-effort, low-risk gap to close (add one SNS topic resource + subscription); no meaningful trade-off against the current approach.

### [Medium] REL-F4 — No safe change-management pattern for runtime/Lambda deploys
- **Evidence:** The AgentCore runtime container is referenced by ECR digest and "a new build updates the runtime in place" (comment, `documentation/terraform/runtime/main.tf:10-13`); Lambdas are updated via direct `source_code_hash` replacement (`documentation/terraform/ingestion/main.tf:171-217`) with no aliases/versions or traffic-shifting configured. Per the shared context pack, there is no CI/CD pipeline (`.github/workflows/` absent) — deploys are manual `terraform apply` runs per module, in order, from a local machine.
- **Impact:** A bad image/code push replaces 100% of production traffic immediately with no canary window and no automated rollback; the only recovery path is a manual `terraform apply` of the previous artifact/digest.
- **Recommendation:** At minimum, pin Lambda versions with an alias and consider `weighted_alias` traffic shifting for the worker; for the AgentCore runtime, keep the previous image digest documented/tagged so a manual rollback is a one-line `terraform apply -var`.
- **Alternative solution:** Given the low-traffic, asynchronous, non-latency-sensitive nature of this workload (documentation generation, not a live user path), full canary/blue-green is likely disproportionate effort for a POC; a documented "keep last-known-good digest, roll back via `terraform apply`" runbook is a reasonable lighter-weight alternative. Pros: near-zero added infra; cons: rollback is manual and detection-dependent (ties to REL-F3). Effort S (documented rollback) to M (Lambda aliases/traffic shifting). Cross-pillar impact: Operational Excellence (deploy pipeline mechanics).

### [Low] REL-F5 — Retry backoff has no jitter
- **Evidence:** `delay = min(max_delay, base_delay * (2 ** (attempt - 1)))` — purely deterministic exponential backoff, no random jitter term — `documentation/scripts/agents/agent-technical-doc/docagent/retry.py:75`.
- **Impact:** Under a correlated failure (e.g., a Bedrock regional throttling event affecting many concurrent worker invocations simultaneously), all retries re-align on the same schedule, which can produce synchronized retry bursts ("thundering herd") against an already-degraded dependency. Blast radius is limited by `worker_max_concurrency = 5` (`documentation/terraform/ingestion/variables.tf:53-57`), so impact is modest at current scale.
- **Recommendation:** Add a jitter term (e.g., full or decorrelated jitter) to `retry_call`'s delay calculation in `documentation/scripts/agents/agent-technical-doc/docagent/retry.py`.
- **Alternative solution:** None needed — this is a small, low-risk code change with no meaningful trade-off.

### [Low] REL-F6 — No documented/tested backup-restore procedure
- **Evidence:** DynamoDB PITR and S3 state-bucket versioning are enabled (`documentation/terraform/security/main.tf:74-76`, `documentation/terraform/bootstrap/main.tf:36-51`), but no restore runbook, restore drill, or restore test was found in `documentation/README.md`, `documentation/AUDIT.md`, or the Terraform tree.
- **Impact:** Backups exist but an actual restore has not been demonstrated to work; RPO/RTO for restoring the idempotency table or Terraform state after corruption is unverified.
- **Recommendation:** Add a one-paragraph restore runbook to the README (`aws dynamodb restore-table-to-point-in-time`, S3 object-version rollback) and, ideally, exercise it once per environment stand-up.
- **Alternative solution:** None — documentation-only fix, negligible effort.
