## Weaknesses / Findings

### [Medium] MNT-F1 — No linter, formatter, or type checker configured or enforced anywhere
- **Evidence:** repo-wide search for `pyproject.toml`, `.flake8`, `ruff.toml`, `setup.cfg`, `.pylintrc`, `mypy.ini`, `.pre-commit-config.yaml` under `/Users/g.mirambeau/Development/AWS/agent-technical-doc` returned no matches; `documentation/scripts/agents/agent-technical-doc/requirements-dev.txt:1-8` lists only `pytest>=8.0`.
- **Impact:** Style/typo/complexity drift is caught only by human review; type hints exist widely but are never statically checked (no `mypy`/`pyright` run), so annotation correctness is unverified. Combined with no CI (see MNT-F2), nothing blocks a regression from merging.
- **Recommendation:** Add `ruff` (lint + format, single fast tool) and `mypy` (or `pyright`) with a minimal `pyproject.toml` config; run both locally via `pre-commit` and in CI.
- **Alternative solution:** Adopt `ruff check` + `ruff format` + `mypy --strict` on `docagent/` only initially (Lambdas are tiny and low-churn) — pros: low effort, fast, single dependency, immediate signal on the highest-value code; cons: doesn't cover Lambda handlers or Terraform; effort S; cross-pillar impact: supports MNT-03/MNT-12 and indirectly Operational Excellence once wired into CI.

### [Medium] MNT-F2 — No CI pipeline exists; test suite and formatting are never enforced automatically
- **Evidence:** no `.github/workflows/`, no other CI config found repo-wide (confirmed by direct `find`); `documentation/README.md:159` self-admits "Phase 4 — industrialisation CI : ⏳ à faire"; `terraform fmt -check` currently fails on one file (`documentation/terraform/ingestion/main.tf`, per context-pack scan) with nothing to catch it before merge.
- **Impact:** 129 passing tests and clean formatting are a snapshot of developer diligence, not a guarantee — nothing prevents a future change from breaking tests or introducing style/type regressions before it lands on `develop`/`main`.
- **Recommendation:** Add a GitHub Actions workflow that runs `pytest` (both suites), `ruff`, and `terraform fmt -check -recursive` on every PR touching `documentation/**`.
- **Alternative solution:** Minimal single-job GitHub Actions workflow (checkout, setup-python, `pip install -r requirements.txt -r requirements-dev.txt`, `pytest`, `ruff check`) — pros: cheap, fast (~1 min given current suite speed), directly closes the README's own stated gap; cons: doesn't cover Terraform validation/plan (would need backend/creds); effort S; cross-pillar impact: Operational Excellence (deployment safety), Reliability (regression prevention).

### [Medium] MNT-F3 — Core LLM-analysis module (`analyzer.py`) has zero test coverage, including its pure/testable functions
- **Evidence:** `documentation/scripts/agents/agent-technical-doc/docagent/analyzer.py:104-121` (`_extract_json` — fence-stripping, brace-scanning JSON extraction from raw LLM text) and `:124-156` (`select_model` — pure cost/complexity-based model selection, explicitly documented as "Fonction pure … testable") have no corresponding test file; repo-wide grep for `analyzer|_extract_json|select_model|BedrockAnalyzer` across `tests/*.py` returns no matches. All other 12 non-trivial `docagent/` modules have direct or clearly-indirect coverage.
- **Impact:** `_extract_json` is the single point of failure translating unstructured LLM output into the structured dict the rest of the pipeline depends on; its edge cases (malformed JSON, missing fences, nested braces in string values, no JSON at all) are unverified. `select_model`'s cost-relevant escalation thresholds (Haiku vs Sonnet) are also unverified despite being pure and cheap to test. Regressions here would only surface at runtime against a real Bedrock call.
- **Recommendation:** Add `tests/test_analyzer.py` covering `_extract_json` (fenced/unfenced/malformed/absent JSON) and `select_model` (file-count and byte-count threshold boundaries, override paths) — both are pure functions requiring no mocking.
- **Alternative solution:** Unit-test the two pure functions directly (as above) — pros: matches the codebase's existing DI/pure-function testing pattern exactly, effort S, closes the highest-risk gap; cons: `BedrockAnalyzer.analyze`/`_build_agent` (the `strands`/`boto3` wiring) would remain untested, but that mirrors the deliberate no-network-test policy already applied elsewhere in the repo; effort S; cross-pillar impact: Reliability (fewer silent parsing failures in production).

### [Low] MNT-F4 — `docagent/__init__.py` `__all__` is stale, listing 8 of 18 modules
- **Evidence:** `documentation/scripts/agents/agent-technical-doc/docagent/__init__.py:10-18` lists only `config, correlation, repo_reader, selection, drawio, doc_builder, github_client, secrets`; the package actually contains 18 modules including `analyzer, comments, committer, github_auth, idempotency, metrics, orchestrator, paths, payload, retry` which are omitted.
- **Impact:** Cosmetic/documentation drift only (Python doesn't enforce `__all__` for direct submodule imports, which is how the code actually imports); a new contributor reading `__init__.py` as a module inventory would get a materially incomplete picture.
- **Recommendation:** Update `__all__` to list all current submodules, or drop it if it's not relied upon for `from docagent import *` semantics.
- **Alternative solution:** None — trivial one-line fix, no alternative needed.

### [Low] MNT-F5 — Dependencies are version-floored (`>=`), not pinned or lock-filed, for the agent runtime
- **Evidence:** `documentation/scripts/agents/agent-technical-doc/requirements.txt:1-9` (`bedrock-agentcore>=0.1.0`, `strands-agents[otel]>=0.1.0`, `boto3>=1.34.0`, `botocore>=1.34.0`, `pyjwt[crypto]>=2.8.0`, `aws-opentelemetry-distro>=0.10.0`); `requirements-dev.txt:8` (`pytest>=8.0`). No `requirements.lock`, `poetry.lock`, or `pip-compile`-generated pinned file found alongside.
- **Impact:** Builds are not reproducible — a fresh `pip install` at a different time can silently pull a newer major/minor version of `strands-agents` or `boto3`, changing behavior (e.g. Bedrock API surface) without a corresponding code change or review trigger. No automated vulnerability/outdated-dependency scanning was found either (no Dependabot/Renovate config, no `pip-audit`/`safety` in CI — and there is no CI, see MNT-F2).
- **Recommendation:** Generate exact-pinned lock files (`pip-compile` from `requirements.txt` → `requirements.lock`, used in the Dockerfile build) and enable Dependabot/Renovate for `documentation/scripts/**/requirements*.txt`.
- **Alternative solution:** Adopt `pip-tools`' `pip-compile` to produce a committed, hash-pinned lock file consumed by the Dockerfile — pros: reproducible builds, still keeps `requirements.txt` as the human-editable source of loose constraints; cons: adds a regeneration step to the dependency-bump workflow; effort S; cross-pillar impact: Security (supply-chain), Reliability (reproducible deploys).

## Notes & assumptions

- Tests were executed read-only (`python3 -m pytest -q`, no `-x`/no fixtures touching real AWS, no `apply`/`init`); this complies with the read-only audit constraint and both dependency sets were already installed in the environment (no packages were installed by this audit).
- The prior run (`audit/20260720-000000/12-maintainability.md`, score 83/100) was not read before forming independent verdicts. This run's score (67/100) is materially lower, driven by strict application of the weighted rubric: MNT-01 (weight 2.0) and MNT-05 (weight 1.5) are the two highest-weighted criteria and both landed Partial (untested `analyzer.py` core-parsing logic; a couple of ~100-120-line functions), while MNT-03 (linter/CI gate) is fully Missing — no config or CI was found anywhere in the repo, confirmed by direct filesystem search rather than relying on the prior claim. The delta is a rubric/weighting effect, not a disagreement about the underlying facts (both runs agree tests exist and pass, and that CI/linting are absent).
- Terraform code itself (IaC formatting/structure) is out of this pillar's scope except where it intersects CI enforcement (MNT-F2 references the known `terraform fmt` failure only as evidence that nothing currently catches such issues).
