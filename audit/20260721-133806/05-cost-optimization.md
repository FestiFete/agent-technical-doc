# Cost Optimization — Audit

**Score:** 82/100  **Maturity:** 4 (Managed)  **Coverage:** 90%  **Confidence:** high
**Applicable:** yes

## Charter & scope
Assess the ability to run at the lowest price point for the required outcome: avoiding waste, right-sizing, pricing-model fit, cost visibility/attribution, and managing spend over time. Excludes raw performance tuning (→ Performance Efficiency) and elastic scaling correctness (→ Scalability).

## Strengths
- End-to-end pay-per-use pricing model: Lambda on-demand (no provisioned/reserved concurrency configured), DynamoDB `PAY_PER_REQUEST`, SQS standard queues, API Gateway HTTP API, and Bedrock AgentCore Runtime (serverless container runtime, billed per session with a bounded idle timeout) — no always-on compute anywhere in the stack — _evidence: `documentation/terraform/security/main.tf:59` (`billing_mode = "PAY_PER_REQUEST"`), `documentation/terraform/ingestion/main.tf:175-206` (Lambda, no `reserved_concurrent_executions`), `documentation/terraform/runtime/main.tf:18-21` (network_mode PUBLIC, no dedicated compute), `documentation/terraform/runtime/data.tf:54-57` (`idle_timeout = 900`, `max_lifetime = 3600`)
- Graviton/ARM64 used for both Lambda functions (roughly 20% cheaper than x86 at equal or better performance) — _evidence: `documentation/terraform/ingestion/main.tf:176`, `documentation/terraform/ingestion/main.tf:204`
- Cost-aware LLM model selection: Haiku by default, with Sonnet escalation gated behind explicit file-count/byte thresholds only for larger repos, plus hard caps on files/bytes read per run — bounds the dominant cost driver (Bedrock token spend) — _evidence: `documentation/scripts/agents/agents.json:6-12` (`MODEL_ID=eu.anthropic.claude-haiku-4-5`, `MODEL_ID_ESCALATION=eu.anthropic.claude-sonnet-4-6`, `MODEL_ESCALATION_MAX_FILES=25`, `MAX_SELECTED_FILES=40`, `MAX_TOTAL_BYTES=1200000`)
- Per-repository run quota (sliding-window, DynamoDB-backed) directly bounds the number of Bedrock-invoking runs a single repo can trigger, capping worst-case spend at the source, independent of API Gateway throttling — _evidence: `documentation/scripts/lambdas/webhook-receiver/handler.py:50` (`max_runs_per_repo` default 20), `documentation/scripts/lambdas/webhook-receiver/handler.py:173-255` (`_rate_limited`, HTTP 429 on quota exceeded)
- API Gateway stage throttling (10 rps / 20 burst) bounds request-driven cost amplification from the public endpoint — _evidence: `documentation/terraform/ingestion/main.tf:257-260`
- ECR lifecycle policy expires untagged images after 1 day and caps tagged image retention to a configurable count (default 10), preventing unbounded storage growth — _evidence: `documentation/terraform/ecr/main.tf:22-49`, `documentation/terraform/ecr/variables.tf:22-26` (`image_retention_count`, default 10)
- CloudWatch Logs retention is explicitly bounded (14 days) and centrally parameterized across both the ingestion Lambdas and the AgentCore runtime log group, avoiding indefinite log accumulation — _evidence: `documentation/terraform/ingestion/main.tf:160`, `documentation/terraform/ingestion/main.tf:165`, `documentation/terraform/ingestion/variables.tf:65-69` (default 14), `documentation/terraform/runtime/logs.tf:7`, `documentation/terraform/runtime/variables.tf:39-43` (default 14)
- SQS message retention is bounded and asymmetric by design (main queue 4 days vs DLQ 14 days), avoiding unbounded queue storage while giving operators a reasonable window to investigate failures — _evidence: `documentation/terraform/ingestion/main.tf:9` (DLQ, 1209600s = 14d), `documentation/terraform/ingestion/main.tf:17` (main, 345600s = 4d)
- DynamoDB idempotency table uses TTL to self-purge stale items, bounding storage growth without manual cleanup — _evidence: `documentation/terraform/security/main.tf:67-70`, `documentation/terraform/security/variables.tf:16-20` (`idempotency_ttl_days`, default 30)
- Consistent cost-attribution tagging (`Project`/`Env`/`Module`) via provider-level `default_tags` applied uniformly across all 7 Terraform modules — _evidence: `documentation/terraform/ingestion/providers.tf:24-29`, `documentation/terraform/bootstrap/main.tf:17-18`, `documentation/terraform/ecr/providers.tf:22-23`, `documentation/terraform/roles/providers.tf:22-23`, `documentation/terraform/runtime/providers.tf:25-26`, `documentation/terraform/observability/providers.tf:21-22`
- No VPC/NAT Gateway anywhere in the stack — the architecture avoids the single largest common source of surprise data-transfer/hourly infra cost (NAT Gateway ~$0.045/hr + per-GB processing) by design, since all compute is public-egress serverless — _evidence: `grep -rn "aws_vpc|nat_gateway|vpc_config" documentation/terraform/` returned no matches (absence verified across all `*.tf` files)
- Worker Lambda invocation is deliberately short-lived (fire-and-forget async `InvokeAgentRuntime`, not a blocking wait on the full agent run), keeping Lambda GB-seconds low regardless of how long the downstream AgentCore analysis takes — _evidence: `documentation/terraform/ingestion/variables.tf:41-45` (comment: "le worker ne fait qu'un appel InvokeAgentRuntime non bloquant (ack immédiat) puis retourne — un timeout court suffit")

## Weaknesses / Findings

### [Medium] COST-F1 — No AWS Budgets or Cost Anomaly Detection configured
- **Evidence:** `grep -rln "aws_budgets|aws_ce_|budgets_budget|anomaly" documentation/terraform/` returns no matches (absence verified); confirmed also absent from README/runbook (`documentation/README.md`) and prior self-audit (`documentation/AUDIT.md:94` lists "AWS Budgets" under "À faire" — to-do, not done)
- **Impact:** No proactive alert exists if Bedrock token spend, Lambda invocation volume, or any other cost driver spikes beyond expectations (e.g., a compromised/malicious allowlisted repo triggering near-quota runs repeatedly, or a bug causing retry storms). Cost visibility is entirely reactive (monthly bill review), with detection relying only on the per-repo run quota and API Gateway throttle as indirect ceilings — there is no direct dollar-denominated guardrail.
- **Recommendation:** Add an `aws_budgets_budget` resource (monthly cost budget with SNS-notified thresholds at e.g. 50%/80%/100% of an expected POC budget) and/or enable AWS Cost Anomaly Detection with a monitor scoped to the project's cost allocation tag (`Project=technical-doc`). Both are free AWS features with no infrastructure cost.
- **Alternative solution:** None needed — this is a pure addition, not a trade-off. Effort: S (a single `aws_budgets_budget` + SNS topic, addable to the existing `observability` module which already centralizes alarms).

### [Low] COST-F2 — No CloudWatch metric/log ingestion cost control beyond retention (no sampling, no log-level tuning)
- **Evidence:** `documentation/scripts/agents/agent-technical-doc/Dockerfile:14` only disables two OTEL instrumentations (`requests,urllib3`); no `OTEL_TRACES_SAMPLER` or equivalent sampling config found (`grep -rn "sampling|OTEL_TRACES_SAMPLER" documentation/` → no matches). Full application + usage logs are delivered via `awscc_logs_delivery` for every run — _evidence: `documentation/terraform/runtime/logs.tf:12-30`
- **Impact:** At current POC volume this is negligible (confirmed by prior self-audit's cost model: `documentation/AUDIT.md:116-118` — "le reste... est négligeable; au repos, quasi zéro"), but log/trace volume scales linearly with run volume with no sampling ceiling, so observability cost is not structurally bounded independent of traffic growth — only time-bounded via the 14-day retention.
- **Recommendation:** If run volume grows materially, consider trace sampling (`OTEL_TRACES_SAMPLER=parentbased_traceidratio` at e.g. 10-20%) and/or reducing usage-log verbosity, while keeping full logs for ERROR-level events.
- **Alternative solution:** None — low priority at current scale; flagging as a forward-looking guardrail rather than a current problem. Effort: S.

### [Low] COST-F3 — No dedicated ephemeral/non-prod environment lifecycle (single POC environment only)
- **Evidence:** `documentation/terraform/shared.tfvars:15-17` (`environment = "POC"`, single value across all modules); no second `tfvars` set or workspace found for a dev/staging split — _evidence: directory listing of `documentation/terraform/` shows only `shared.tfvars` and `ingestion/terraform.tfvars`
- **Impact:** COST-03 (scale-to-zero for non-prod) and COST-09 (ephemeral env teardown) are not directly demonstrable because there is no separate non-prod environment to observe being torn down or scheduled — the project currently only has one environment, which happens to already be fully scale-to-zero by construction (serverless throughout). This is a low-severity gap since the single environment's idle cost is already near-zero, but if a second (e.g., staging) environment is added later without a teardown/schedule mechanism, idle cost would appear.
- **Recommendation:** If/when a second environment is introduced, document or automate its teardown (e.g., a scheduled `terraform destroy` for ephemeral test stacks, or reuse of the existing scale-to-zero architecture which requires no special non-prod handling since nothing runs idle).
- **Alternative solution:** None — the current single-environment, fully-serverless design sidesteps the need for explicit non-prod scheduling. Effort: N/A (informational).

## Notes & assumptions
- This is explicitly a POC-scale, single-environment deployment (`environment = "POC"` throughout); several criteria (COST-03 non-prod scaling, COST-09 ephemeral teardown) are evaluated as Partial/N/A because the *artifact they'd apply to* (a distinct non-prod environment) does not exist yet, not because the existing environment is poorly managed — the existing single environment is itself already fully scale-to-zero.
- `terraform validate`/`plan` were not run (per context pack, out of scope for this static-only pass); all verdicts are based on static `.tf`/`.py`/`.json` file inspection only.
- The prior run's simplified 3-criterion grid (`audit/20260720-000000/05-cost-optimization.md`, score 88/100) is not directly comparable to this run's 11-criterion WAF-aligned grid; the score difference reflects a stricter/expanded rubric (adding COST-06 budgets as Missing, and splitting non-prod/observability-sampling nuances the prior run collapsed into a single "Partial" governance note), not a regression in the underlying architecture.
- Cost allocation tagging (COST-05) is consistent but the `security` module explicitly omits `default_tags`/resource tags on the DynamoDB table to avoid a `kms:TagResource` permission gap (`documentation/terraform/security/main.tf:78`, `documentation/terraform/security/providers.tf:22`) — a deliberate, documented exception rather than an oversight, so COST-05 is still scored Met at the module-provider level (6 of 7 modules tag consistently; the security module's resource-level tag omission is a narrow, explained gap).
