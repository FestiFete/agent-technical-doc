## Charter & scope
Assesses the overall system design of `agent-technical-doc`: fitness of the event-driven serverless style, component boundaries, data flow/ownership, integration patterns (sync/async), consistency/idempotency strategy, state placement, cross-cutting concerns, documentation-vs-code fidelity, avoidance of accidental complexity, failure-domain isolation, technology consistency, and extensibility. Internal module granularity is deferred to Modularity (09); coupling mechanics to Decoupling (10); load behaviour to Scalability (11); security/reliability specifics to 02/03 (noted here only where they reveal an architectural boundary issue).

## Strengths
- Clean, single-direction event-driven pipeline (API Gateway → webhook Lambda → SQS → worker Lambda → `InvokeAgentRuntime` → AgentCore runtime) with each hop doing one job and no component reaching backward across the chain — _evidence: `documentation/scripts/lambdas/webhook-receiver/handler.py:217-265`, `documentation/scripts/lambdas/worker-dispatcher/handler.py:80-96`_
- Explicit, enforced least-authority boundary: the webhook Lambda never holds the GitHub token — PR resolution/clone/commit is deferred to the agent, which is the only component with `GitHubTokenRead` — _evidence: `documentation/scripts/lambdas/webhook-receiver/handler.py:1-14`, `documentation/terraform/roles/main.tf:66-70`, `documentation/scripts/agents/agent-technical-doc/docagent/orchestrator.py:110-126`_
- Coherent, well-reasoned idempotency/consistency strategy across two independent boundaries: webhook-side dedup by `repo#pr#comment_id` (delivery-level) and agent-side strong claim by `repo#pr#sha` (result-level), with an explicit claim/release lifecycle (release only on failure, kept on success) — _evidence: `documentation/scripts/agents/agent-technical-doc/docagent/idempotency.py:22-75`, `documentation/scripts/lambdas/webhook-receiver/handler.py:140-163`, `documentation/scripts/agents/agent-technical-doc/docagent/orchestrator.py:204-213,252-258`_
- Deliberate, well-documented statelessness: the agent has no AgentCore Memory/Knowledge Base, all config is env-derived with safe defaults, and all durable state is externalized to one DynamoDB table with namespaced key prefixes (`repo#pr#sha`, `repo#pr#comment_id`, `ratelimit#…`) — _evidence: `documentation/scripts/agents/agent-technical-doc/agent.py:17-18`, `documentation/scripts/agents/agent-technical-doc/docagent/config.py:1-96`, `documentation/terraform/security/main.tf:54-79`_
- Async invocation pattern matches the workload: worker gets an immediate ack (~1s) via `add_async_task`/`HealthyBusy`, freeing Lambda concurrency, while the agent remains responsible for terminal restitution (commit + comment) — _evidence: `documentation/scripts/agents/agent-technical-doc/agent.py:77-119`_
- Failure-domain isolation is intentional and layered: SQS+DLQ isolates ingestion failures from the runtime, worker classifies transient vs. permanent errors to avoid useless replay loops, and the agent's internal retry only replays idempotent reads (analysis), never the commit — _evidence: `documentation/scripts/lambdas/worker-dispatcher/handler.py:25-77`, `documentation/scripts/agents/agent-technical-doc/docagent/retry.py:1-30`, `documentation/scripts/agents/agent-technical-doc/docagent/orchestrator.py:67-77`_
- Consistent, single-stack technology choices with justified exceptions (Terraform `awscc` only for the one AgentCore-runtime resource not yet in the AWS provider; Python 3.11 slim base for the agent vs. 3.12 Lambda runtime is a deliberate base-image choice, not drift) — _evidence: `documentation/terraform/runtime/main.tf:3`, `documentation/scripts/agents/agent-technical-doc/Dockerfile`_
- `ARCHITECTURE.md`'s two Mermaid diagrams and component inventory match the current on-disk code and Terraform almost exactly, including the working-tree-uncommitted IAM narrowing (`ConsumeQueue` = `ReceiveMessage`/`DeleteMessage` only, no `GetQueueAttributes`) — _evidence: `documentation/ARCHITECTURE.md:26-83`, `documentation/terraform/ingestion/main.tf:137-143`_
- Remote-state dependency chain across the 7 Terraform modules exactly matches the documented deploy order (`bootstrap → ecr → security → roles → runtime → ingestion → observability`), with no back-references or cycles — _evidence: `documentation/terraform/roles/data.tf:7,16`, `documentation/terraform/runtime/data.tf:5,14,23`, `documentation/terraform/ingestion/data.tf:7,16`_

## Weaknesses / Findings

### [Low] ARC-F1 — Dead/mismatched IAM statement for the rate-limit DynamoDB write path
- **Evidence:** `documentation/terraform/ingestion/main.tf:82-92` (`RateLimitQuery` statement grants `dynamodb:Query` gated on `LeadingKeys = ["${var.mention_handle}#*"]`, i.e. keys prefixed `@agent-technical-doc#*`) vs. `documentation/scripts/lambdas/webhook-receiver/handler.py:184-213` (`_increment_repo_counter` actually calls `UpdateItem` on keys prefixed `ratelimit#…`, an operation already separately covered by the unconditional `ClaimIdempotency` statement at `documentation/terraform/ingestion/main.tf:76-81`).
- **Impact:** The `RateLimitQuery` statement neither authorizes the action the code performs (`UpdateItem`, not `Query`) nor matches the key prefix actually used (`ratelimit#`, not the mention handle). It is inert — the real rate-limit write path is authorized instead by the broad, unconditional `ClaimIdempotency` grant. This is a design/documentation-vs-implementation drift: the IAM policy models an access pattern that doesn't exist, while the pattern that does exist is granted more broadly than intended, undermining the "least privilege, scoped by condition" narrative the surrounding code comments assert. Low severity architecturally (no functional break, caught by IAM/Security pillar rather than here), but it signals that a cross-cutting concern (authorization) drifted from the data-flow it was meant to model.
- **Recommendation:** Either implement the rate limiter with a `Query`+condition matching this statement, or remove `RateLimitQuery` and add an explicit, correctly-scoped condition (`dynamodb:LeadingKeys = ["ratelimit#*"]`) to the statement that actually grants `UpdateItem` for counters.
- **Alternative solution:** None — this is a small, self-contained fix, not a design-alternative-worthy issue. Cross-reference: primarily a Security-pillar (IAM correctness) finding; flagged here only for the architecture/implementation-fidelity angle.

### [Info] ARC-F2 — Single DynamoDB table multiplexes three distinct data-ownership domains
- **Evidence:** `documentation/terraform/security/main.tf:54-79` (one `idempotency` table, hash key `pk`); consumers: webhook dedup key `repo#pr#comment_id` (`documentation/scripts/lambdas/webhook-receiver/handler.py:244`), webhook rate-limit key `ratelimit#{repo}#{bucket}` (`documentation/scripts/lambdas/webhook-receiver/handler.py:179-181`), agent strong-claim key `repo#pr#sha` (`documentation/scripts/agents/agent-technical-doc/docagent/correlation.py` via `orchestrator.py:38-39`).
- **Impact:** Three semantically different concerns (delivery dedup, quota counting, run-level idempotency) share one table and one attribute schema, distinguished only by key-prefix convention rather than by structural separation (e.g. separate tables, GSI, or item type attribute). This is workable at current scale and the prefixes are consistent and well-documented, so it is not a correctness risk today — but it is exactly the kind of "shared state across boundaries" that criterion ARC-03 flags as worth watching, since a future feature reusing the table without knowing all three conventions could collide on key format or TTL semantics.
- **Recommendation:** No immediate action needed; if a fourth consumer of this table is ever added, prefer a dedicated table or a `type` discriminator attribute over a fourth ad hoc prefix.
- **Alternative solution:** None — informational, POC-appropriate as-is.
