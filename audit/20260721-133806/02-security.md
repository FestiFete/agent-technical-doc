# Security — Audit

## Charter & scope
Covers confidentiality, integrity, and availability controls: identity & access management, data protection (at rest/in transit), network security, secrets management, detective controls, and secure SDLC.

Does **not** cover: backup/DR mechanics for availability (→ Reliability pillar, 03), or general IaC hygiene/module structure (→ Terraform pillar, 08) — this pillar only covers the security *content* of the IaC (policies, encryption, exposure).

## Strengths
- Recent IAM tightening commits (SEC-01/02/03 in git log) plus an uncommitted further narrowing are real and verified on disk: webhook role scoped to `dynamodb:PutItem/UpdateItem/Query` (with a `dynamodb:LeadingKeys` condition) and `sqs:SendMessage` (with an `sqs:QueueName` condition); worker role scoped to exactly `sqs:ReceiveMessage`/`sqs:DeleteMessage` and `bedrock-agentcore:InvokeAgentRuntime` on a single runtime ARN — _evidence: `documentation/terraform/ingestion/main.tf:64-153`_
- Webhook authenticity is enforced with a constant-time HMAC-SHA256 check on `X-Hub-Signature-256`, executed before any payload parsing or AWS resource access, minimizing pre-auth cost — _evidence: `documentation/scripts/lambdas/webhook-receiver/handler.py:56-63`, `documentation/scripts/lambdas/webhook-receiver/handler.py:217-226`_
- Per-service IAM roles with no sharing: `webhook`, `worker`, and `runtime_execution` each have a distinct role and inline policy limited to what that component needs — _evidence: `documentation/terraform/ingestion/main.tf:54-153`, `documentation/terraform/roles/main.tf:3-81`_
- No long-lived static credentials: GitHub auth prefers a GitHub App with short-lived (~1h) installation tokens obtained via RS256 JWT exchange; Secrets Manager values are set out-of-band (`ignore_changes` lifecycle, placeholder `REPLACE_ME` in state) rather than embedded in Terraform — _evidence: `documentation/scripts/agents/agent-technical-doc/docagent/github_auth.py:87-151`, `documentation/terraform/security/main.tf:26-37,45-52`_
- Secret values are never logged, only key names; a dedicated `mask_secrets` redaction helper is applied to any exception text that might echo secret material — _evidence: `documentation/scripts/agents/agent-technical-doc/docagent/secrets.py:44-60`, `documentation/scripts/agents/agent-technical-doc/docagent/correlation.py:35-49`, `documentation/scripts/agents/agent-technical-doc/docagent/orchestrator.py:191,202,258,266`_
- Untrusted repository content (tarball from GitHub) is extracted with explicit tar-slip / symlink / hard-link / device-file protections and the codebase contains no `subprocess`/`os.system`/`shell=True` calls, closing the most obvious injection surfaces — _evidence: `documentation/scripts/agents/agent-technical-doc/docagent/repo_reader.py:29-59`_
- All data stores are encrypted at rest with AWS-managed keys (SSE-SQS on both queues, S3 SSE-KMS on the state bucket, DynamoDB/Secrets Manager default encryption, ECR AES256) — this is a real, verifiable improvement over "no encryption," even though it stops short of customer-managed keys (see SEC-F2) — _evidence: `documentation/terraform/ingestion/main.tf:8,14`, `documentation/terraform/bootstrap/main.tf:43-51`, `documentation/terraform/ecr/main.tf:13-15`_

## Weaknesses / Findings

### [Medium] SEC-F1 — Public webhook API Gateway endpoint has no WAF / L7 protection
- **Evidence:** `documentation/terraform/ingestion/main.tf:234-261` (no `aws_wafv2_web_acl` or association anywhere in the module); repo-wide grep for `wafv2` across `documentation/terraform/**/*.tf` returns no matches.
- **Impact:** The only pre-Lambda controls on the public `POST /webhook` route are API Gateway stage throttling (`throttling_burst_limit=20`, `throttling_rate_limit=10`, `documentation/terraform/ingestion/main.tf:257-260`) and the in-Lambda HMAC check. There is no L7 filtering (managed rule sets, bot control, rate-based rules per source IP) in front of the endpoint, so malformed/abusive traffic still reaches a live Lambda invocation before being rejected.
- **Recommendation:** Attach an AWS WAFv2 WebACL (AWS Managed Rules: Core rule set + Known Bad Inputs, plus an IP rate-based rule) to the HTTP API stage as defense-in-depth alongside the existing HMAC verification.
- **Alternative solution:** Keep current app-level HMAC + throttle only vs. add WAFv2. Pros of adding WAF: catches malformed/scanning traffic before Lambda cost is incurred, per-IP rate limiting independent of the account-wide API GW throttle, managed rule updates. Cons: added monthly cost and one more component to manage for a POC-scale system. Effort: S. Cross-pillar impact: Cost Optimization (small added spend), Reliability (extra protection against volumetric abuse of the ingestion path).

### [Low] SEC-F2 — No customer-managed KMS keys (CMK); encryption relies solely on AWS-owned/AWS-managed keys, and this is currently blocked at the account level
- **Evidence:** `documentation/terraform/security/main.tf:8-13,23,42` ("CMK KMS retirée : le rôle NewSysOps a un DENY explicite sur `kms:CreateKey`"), `documentation/terraform/ingestion/main.tf:104,150`, `documentation/terraform/roles/main.tf:77-78`.
- **Impact:** Every data store (Secrets Manager, DynamoDB, SQS, S3 state bucket) uses AWS-managed/owned keys rather than a project-scoped CMK, so there is no customer-controlled key policy, no configurable rotation cadence, and CloudTrail key-usage attribution is coarser than with a dedicated CMK. This is documented in-repo as a deliberate, account-policy-driven POC compromise rather than an oversight.
- **Recommendation:** Before promoting beyond POC, request the narrow `kms:CreateKey`/key-management permissions needed (or have the account's security team provision a project CMK), then re-enable `kms_key_id` on Secrets Manager/DynamoDB/S3 and enable automatic key rotation.
- **Alternative solution:** Current AWS-managed keys vs. introducing a CMK. Pros of CMK: key policy control, configurable rotation, cross-account access boundary, fine-grained CloudTrail key-usage logs. Cons: added operational overhead/cost, and it is currently blocked by an org-level IAM deny outside this project's control. Effort: M (dependent on an org-level permissions change).

### [Medium] SEC-F3 — No account/project-level detective controls (CloudTrail, Config, GuardDuty, Security Hub)
- **Evidence:** repo-wide grep across `documentation/terraform/` for `cloudtrail|aws_config|guardduty|securityhub` returns no matches; `documentation/terraform/observability/main.tf:1-100` defines only CloudWatch alarms/dashboard for operational signals (DLQ depth, Lambda error counts), not security event detection; no `access_log_settings` block is configured on the API Gateway stage in `documentation/terraform/ingestion/main.tf`.
- **Impact:** No centralized, immutable audit trail of API/IAM activity and no continuous threat/posture detection. An IAM policy change, unusual `secretsmanager:GetSecretValue` pattern, or anomalous `bedrock-agentcore:InvokeAgentRuntime` call would not be independently detected outside of what the application's own CloudWatch logs happen to capture.
- **Recommendation:** Enable an account/org CloudTrail trail and CloudWatch Logs metric filters/alarms on IAM policy changes and unusual Secrets Manager access for these specific resources at minimum; consider GuardDuty for lightweight always-on threat detection given this is a POC-scale account.
- **Alternative solution:** None — a baseline CloudTrail trail is a foundational, low-cost AWS control with no reasonable justification to omit even at POC scale. Effort: S.

### [Low] SEC-F4 — Bedrock model-invoke permission scoped wider than the models actually used
- **Evidence:** `documentation/terraform/roles/main.tf:42-49` (`Resource = ["arn:aws:bedrock:*::foundation-model/*", "arn:aws:bedrock:*:${account_id}:inference-profile/*"]`) vs. `documentation/scripts/agents/agents.json:5-6` (`MODEL_ID=eu.anthropic.claude-haiku-4-5`, `MODEL_ID_ESCALATION=eu.anthropic.claude-sonnet-4-6`).
- **Impact:** The runtime execution role can invoke any foundation model in any region, not just the two Claude models actually configured. No direct exploit path was identified in this review, but this is unnecessary blast-radius given the role's other permissions are otherwise tightly scoped (see strengths above).
- **Recommendation:** Scope the `BedrockInvoke` statement's `Resource` to the specific model/inference-profile ARNs and region (`eu-central-1`) actually used.
- **Alternative solution:** None needed — straightforward tightening consistent with the existing least-privilege pattern already applied elsewhere in this module. Effort: S.

### [Low] SEC-F5 — Unpinned Python dependencies, no lockfile
- **Evidence:** `documentation/scripts/agents/agent-technical-doc/requirements.txt:1-8` (`bedrock-agentcore>=0.1.0`, `strands-agents[otel]>=0.1.0`, `boto3>=1.34.0`, `botocore>=1.34.0`, `pyjwt[crypto]>=2.8.0`, `aws-opentelemetry-distro>=0.10.0`); no `.lock`/pip-compile output found in the repo (only unrelated `.venv` internal lock files).
- **Impact:** Container builds are not reproducible and can silently pick up new — possibly vulnerable or breaking — dependency versions between builds; there is no deterministic dependency graph to run vulnerability scanning against at the Python-package level (ECR's `scan_on_push` only covers the built image, not a pinned source-of-truth for what should be in it).
- **Recommendation:** Pin exact versions (or generate a lockfile via `pip-compile`/`uv lock`) and add periodic scanning (`pip-audit`, Dependabot/Renovate for Python deps).
- **Alternative solution:** None needed. Effort: S.

## Notes & assumptions
- Static analysis only (`live_aws=OFF`); no AWS API calls were made, so IAM policies were validated by reading their JSON bodies in Terraform source, not by simulating access (e.g., `iam simulate-custom-policy`) or inspecting live resource policies/bucket ACLs.
- The prior run's `SEC-F1` ("Publicly exposed entrypoint without WAF and without CMK-backed encryption controls", rated Critical) was independently re-verified: the "no WAF" condition still holds (kept here as SEC-F1, downgraded to Medium — the HMAC check runs before any expensive processing and API Gateway throttling caps request rate, so this is a defense-in-depth gap rather than an exploitable hole) and the "no encryption at rest" framing was found to be inaccurate — all data stores **are** encrypted at rest with AWS-managed keys; only customer-managed keys (CMK) are absent, which is now tracked separately as SEC-F2 (Low) and reflected in SEC-03 (Met) vs. SEC-07 (Missing). This is the main reason this run's score (79) is higher than the prior run's (68).
- No Critical-severity findings were identified in this review (no exploitable hole, unauthenticated write path, or public-writable data store was found), so the pillar maturity is not capped at 2/5 by the capping rule.
- `terraform validate`/`plan` were not run (no `init -backend=false`, per context pack — time-boxed); all conclusions are from reading `.tf` source directly, cross-checked against the actual Lambda/agent Python source.
- Coverage is high (~95%) for in-scope Terraform modules and the Lambda/agent code paths relevant to security; not independently assessed: actual IAM Access Analyzer / policy-simulator results (no live AWS access this run), the contents of `ingestion/terraform.tfvars` (allowlist config, not dumped per context pack — treated as non-secret config), and any manual/undocumented AWS console configuration outside Terraform (e.g., manually-set bucket policies) which by definition is invisible to a static repo audit.
