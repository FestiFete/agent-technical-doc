# Decoupling — Audit

**Score:** 87/100  **Maturity:** 4 (Managed)  **Coverage:** 75%  **Confidence:** medium
**Applicable:** yes

## Charter & scope
Assess how loosely components/services depend on each other at runtime and build time: dependency inversion, async/event-driven boundaries, contract stability, and the ability to change/deploy one part without breaking others. Excludes static decomposition/cohesion (Modularity, pillar 09), overall style choice (Architecture, pillar 07), and elastic independent scaling (Scalability, pillar 11).

This re-verification independently re-examined the webhook → SQS → worker → AgentCore chain, the `InvokeAgentRuntime` call semantics (sync vs. fire-and-forget), the `terraform_remote_state` deploy graph across the 7 Terraform modules, and the config/secret injection patterns in `docagent/config.py` and `docagent/secrets.py`. The prior run (`audit/20260720-000000/10-decoupling.md`, score 87/100) filled only 3 of the 10 required criteria and cited coarse evidence ranges; this run independently fills all 10 criteria with line-level evidence. The resulting score (87) coincidentally matches the prior run's number, but rests on materially different (fuller, more granular) evidence.

## Strengths
- SQS main+DLQ queue decouples webhook ingress from worker processing, with bounded retention (4d/14d), a visibility timeout tuned to the worker timeout, and a redrive policy — _evidence: `documentation/terraform/ingestion/main.tf:6-23`_
- The worker's `InvokeAgentRuntime` call is genuinely fire-and-forget: the AgentCore entrypoint validates the payload, spawns the real work (clone → LLM analysis → commit → PR comment) on a background thread via `add_async_task`/`complete_async_task`, and returns an `"accepted"` ack immediately — so the worker Lambda's declared timeout is only 60s by design — _evidence: `documentation/scripts/agents/agent-technical-doc/agent.py:19-31,52-98`, `documentation/terraform/ingestion/variables.tf:41-45`_
- The orchestrator uses explicit dependency injection: `OrchestratorDeps` is a dataclass of injectable `Callable`s (`get_token`, `make_client`, `fetch_repo`, `analyze`, `claim_idempotency`, `release_idempotency`), with real implementations wired lazily by `default_deps()` — high-level run logic depends on abstractions, not concretions — _evidence: `documentation/scripts/agents/agent-technical-doc/docagent/orchestrator.py:34-91`_
- Config and secrets are injected, never hardcoded: all tunables read from environment variables with safe defaults, and the GitHub credential is fetched by Secrets Manager ARN at call time (never embedded) — _evidence: `documentation/scripts/agents/agent-technical-doc/docagent/config.py:12-96`, `documentation/scripts/agents/agent-technical-doc/docagent/secrets.py:44-60`, `documentation/terraform/ingestion/main.tf:182-194,210-214`_
- The 7-module Terraform graph (`bootstrap → ecr/security → roles → runtime → ingestion → observability`) is wired exclusively through `terraform_remote_state` outputs and is acyclic — no module reads a module that (transitively) reads it back — _evidence: `documentation/terraform/roles/data.tf:1-27`, `documentation/terraform/runtime/data.tf:1-35`, `documentation/terraform/ingestion/data.tf:1-30`, `documentation/terraform/observability/main.tf:1-13`_
- Failure isolation: the worker classifies transient vs. permanent SQS-message errors (permanent errors are absorbed/logged, not retried, avoiding retry storms) and the orchestrator's top-level `try/except` guarantees a terminal PR comment plus idempotency release on any failure, so a run failure never crashes or blocks the webhook/worker infra — _evidence: `documentation/scripts/lambdas/worker-dispatcher/handler.py:25-33,71-95`, `documentation/scripts/agents/agent-technical-doc/docagent/orchestrator.py:249-269`_

## Weaknesses / Findings
### [Medium] DEC-F1 — Shared DynamoDB table used as cross-component state store with no documented key-schema contract
- **Evidence:** `documentation/terraform/security/main.tf:57-58` (single `idempotency` table), `documentation/terraform/ingestion/main.tf:76-92` (webhook role: `PutItem`/`UpdateItem`/`Query`), `documentation/terraform/roles/main.tf:74-75` (agent runtime role: `PutItem`/`DeleteItem`/`GetItem`/`UpdateItem`), `documentation/scripts/lambdas/webhook-receiver/handler.py:140-163,179-213` (webhook writes keys `repo#pr#comment_id` and `ratelimit#{repo}#{bucket}`), `documentation/scripts/agents/agent-technical-doc/docagent/idempotency.py:22-52` (agent writes/deletes keys `repo#pr#sha`)
- **Impact:** Two independently deployable components (webhook Lambda, AgentCore runtime) both read/write one physical DynamoDB table with no schema owner or interface boundary — only an informal key-naming convention keeps the two key namespaces from colliding. A future change to either component (e.g. a key-format change, a new attribute, a TTL semantics change) is not guarded by any contract test and could silently corrupt the other component's records. Currently low-probability because the namespaces (`repo#pr#comment_id`, `ratelimit#...`, `repo#pr#sha`) don't overlap, but nothing enforces that going forward.
- **Recommendation:** Document the shared key-schema contract explicitly (e.g. a small shared constants/prefix module referenced by both codebases, or a comment block in `security/main.tf`), or split into two tables (dedup/idempotency vs. rate-limiting) each scoped to a single owning component's IAM policy.
- **Alternative solution:** Two dedicated tables, one per concern, each with its own least-privilege IAM statement. Pros: clear ownership, smaller blast radius, easier independent schema evolution. Cons: one more resource to manage; negligible extra cost at POC scale. Effort: S. Cross-pillar impact: Security (roles/09 modularity — cleaner IAM scoping).

### [Low] DEC-F2 — No explicit contract versioning on the webhook→SQS→worker→AgentCore payload
- **Evidence:** `documentation/scripts/agents/agent-technical-doc/docagent/payload.py:26-58` (`InvocationRequest`, no version field, only `repo_full_name`/`pr_number` required), `documentation/scripts/lambdas/worker-dispatcher/handler.py:55-60` (builds the AgentCore payload dict inline), `documentation/scripts/lambdas/webhook-receiver/handler.py:258-263` (builds the SQS message dict inline)
- **Impact:** The three producers/consumers (webhook Lambda, worker Lambda, AgentCore agent) agree on the payload shape only by convention (no schema, no version tag, no contract test). A future breaking rename deployed to one Lambda without the others would fail silently or be misinterpreted rather than being caught early. Partially mitigated today by a tolerant-reader pattern (only 2 fields required; the rest are optional and re-resolved by the agent via the GitHub API).
- **Recommendation:** Add a `schema_version` field to the SQS/AgentCore payloads and validate it on the consuming side; add a lightweight consumer-contract test that pins the current message shape.
- **Alternative solution:** Adopt a small shared payload-schema module (dataclass or JSON Schema) imported/validated by both the Lambdas and the agent package. Pros: fail-fast on drift, self-documenting. Cons: adds a shared-code dependency between the two currently-independent codebases (Lambdas vs. agent package), and there is no CI today to run contract tests automatically. Effort: S.

### [Low] DEC-F3 — Terraform module chain is a fixed, deploy-time-coupled sequence (not independently deployable)
- **Evidence:** `documentation/terraform/ingestion/main.tf:122-131` (worker IAM policy has a `lifecycle.precondition` that fails the `ingestion` apply if the `runtime` module's ARN output is empty), `documentation/terraform/ingestion/data.tf:12-19,30` (runtime ARN sourced from `runtime` module's remote state), `documentation/terraform/runtime/data.tf:1-35` (runtime module reads `ecr`, `roles`, `security` remote state), `documentation/terraform/roles/data.tf:3-27` (roles module reads `ecr`, `security` remote state)
- **Impact:** The 7 modules must be applied in exactly one order (`bootstrap → ecr/security → roles → runtime → ingestion → observability`); an out-of-order or partial apply is explicitly rejected by a `precondition` rather than silently producing broken infra, which is good, but it means the modules are not independently deployable — any output rename in an upstream module forces a coordinated re-apply chain, and there is no CI (per context pack) to catch an apply-order regression automatically.
- **Recommendation:** Keep the layering (reasonable for a 7-module POC) but keep the deploy-order documentation current (README already states the order) and consider a thin CLI/script check that validates remote-state outputs exist before each `apply`, given there's no CI to enforce this.
- **Alternative solution:** None proposed — full independent deployability of these infra layers is not warranted at this project's scale; S3-remote-state layering with explicit preconditions is a reasonable, standard Terraform pattern and already fails safely rather than partially. Not Critical/High, no alternative required.

### [Info] DEC-F4 — Retry-on-transient-error wrapping covers only the Bedrock `analyze()` call, not GitHub API calls
- **Evidence:** `documentation/scripts/agents/agent-technical-doc/docagent/orchestrator.py:67-77` (`retry_call` wraps only `analyzer.analyze`), `documentation/scripts/agents/agent-technical-doc/docagent/orchestrator.py:110-126,227-240` (`get_pull_request`, `commit_documents`, `post_issue_comment` are called directly, no `retry_call`)
- **Impact:** A single transient GitHub 5xx during PR resolution, commit, or comment posting fails the whole run. This is not a cascading failure — the outer `try/except` in `_execute` still guarantees a failure comment and releases the idempotency claim so a human/re-mention can retry — but it is an avoidable manual step for a case the codebase already has the tooling (`retry.py`) to handle.
- **Recommendation:** Wrap the idempotent GitHub calls (`get_pull_request`, read-only calls) with the existing `retry_call` helper; consider it for `post_issue_comment`/commit too if GitHub write-idempotency is confirmed safe.
- **Alternative solution:** None needed — Info severity, self-healing already exists via idempotency release + manual re-mention.
