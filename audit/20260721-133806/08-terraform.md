# Terraform (Structure & Best Practices) — Audit

**Score:** 77/100  **Maturity:** 4 (Managed)  **Coverage:** 90%  **Confidence:** high
**Applicable:** yes

## Charter & scope
Assesses Terraform/IaC engineering quality: repository/module structure, state management, versioning, variable/output hygiene, provider config, safety, and idiomatic style, across the 7 modules under `documentation/terraform/` (`bootstrap`, `ecr`, `security`, `roles`, `runtime`, `ingestion`, `observability`). Does not cover the security *content* of IaC (→ Security pillar), whether the deployed architecture is sound (→ Architecture pillar), or reuse-granularity philosophy (→ Modularity pillar).

## Strengths
- Consistent per-module layout: every module has `main.tf`/`variables.tf`/`providers.tf` (+ `data.tf`/`outputs.tf` where relevant), each with its own isolated S3-backed state and a clean dependency chain via `terraform_remote_state` — `roles` reads `ecr`+`security` (`documentation/terraform/roles/data.tf:3-19`), `ingestion` reads `security`+`runtime` (`documentation/terraform/ingestion/data.tf:1-18`), `observability` reads `ingestion` (per inventory). — _evidence: `documentation/terraform/roles/data.tf:3-19`, `documentation/terraform/ingestion/data.tf:3-18`_
- All 7 modules have a committed `.terraform.lock.hcl` (26-69 lines each, hash-pinned providers) and every module pins `required_version >= 1.6.0` and `aws ~> 6.0`. — _evidence: `documentation/terraform/ingestion/.terraform.lock.hcl:1-5`, `documentation/terraform/ingestion/providers.tf:1-10`_
- No Terraform state, `.tfvars` secrets, or plan artifacts are actually tracked in git; `.gitignore` explicitly excludes `**/.terraform/*` and `*.tfstate*`, and `git check-ignore`/`git ls-files` confirm the local `ingestion/.terraform/` residue (provider cache + `terraform.tfstate` backend-cache file) referenced in the task brief is untracked local dev leftover, not a committed-state incident. — _evidence: `documentation/.gitignore:2-3`; `git check-ignore -v documentation/terraform/ingestion/.terraform/terraform.tfstate` → matched `.gitignore:3`; `git ls-files documentation/terraform/ingestion/.terraform/` → empty_
- All variables across all 7 modules are typed and carry a `description`; sensible defaults are set for tunables (timeouts, retention, thresholds) while required cross-module inputs (`state_bucket` in `roles`/`runtime`/`ingestion`/`observability`) are left mandatory. — _evidence: `documentation/terraform/ingestion/variables.tf:1-70`, `documentation/terraform/observability/variables.tf:1-25`_
- Deliberate, well-commented `lifecycle` usage on stateful/critical resources: `ignore_changes = [secret_string]` on both Secrets Manager secrets (values managed out-of-band), and `precondition` blocks that fail fast if an upstream module wasn't deployed yet. — _evidence: `documentation/terraform/security/main.tf:34-36,49-51`, `documentation/terraform/ingestion/main.tf:126-131`, `documentation/terraform/runtime/build.tf:6-11`_
- Idiomatic `for_each` used throughout for multi-instance resources (log groups, alarms, runtime agents, build artifacts); no bare `count` found anywhere in the codebase, avoiding fragile index-based addressing. — _evidence: `documentation/terraform/runtime/logs.tf:4,13,23,33,41,53,66,80`, `documentation/terraform/runtime/main.tf:4`, `documentation/terraform/runtime/build.tf:15,38`_
- Explicit `depends_on` used where implicit dependency inference is insufficient (IAM policy attachment before Lambda creation, log group before Lambda, ECR image before runtime). — _evidence: `documentation/terraform/ingestion/main.tf:196,216`, `documentation/terraform/runtime/build.tf:34,43`_
- Tagging is applied consistently via `default_tags` on the `aws` provider in 5 of 7 modules (`Project`/`Env`/`Module`), with the one deliberate exception (`security`) explained in-code (avoiding `kms:TagResource` under a restricted deploy role) rather than an oversight. — _evidence: `documentation/terraform/ecr/providers.tf:19-25`, `documentation/terraform/security/providers.tf:14-17`_
- Account ID is correctly sourced from `data.aws_caller_identity.current` (not hardcoded) in resource-level ARNs outside backend blocks. — _evidence: `documentation/terraform/roles/data.tf:1,21-23`, `documentation/terraform/ingestion/data.tf:1,20`_
- Recent commit history (`SEC-01`..`SEC-03`, and the uncommitted working-tree diff removing `sqs:GetQueueAttributes` from the worker role) shows an active, disciplined least-privilege tightening practice on IAM policies authored directly in Terraform. — _evidence: `git log --oneline -5`; `documentation/terraform/ingestion/main.tf:137-142` (working tree)_

## Weaknesses / Findings

### [High] TF-F1 — No state locking configured on any S3 backend (no DynamoDB lock table, no S3 native locking)
- **Evidence:** `documentation/terraform/ecr/providers.tf:12-17`, `documentation/terraform/ingestion/providers.tf:12-17`, `documentation/terraform/security/providers.tf:9-14`, `documentation/terraform/roles/providers.tf:9-14`, `documentation/terraform/runtime/providers.tf:12-18`, `documentation/terraform/observability/providers.tf:9-14` (no `dynamodb_table` and no `use_lockfile` in any `backend "s3"` block); confirmed via local backend-cache: `documentation/terraform/ingestion/.terraform/terraform.tfstate:15,49` and `documentation/terraform/runtime/.terraform/terraform.tfstate:15,49` both show `"dynamodb_table": null` / `"use_lockfile": null`.
- **Impact:** All 6 S3-backed modules (everything except `bootstrap`, which is local-backend by design) can suffer concurrent-apply state corruption if two operators (or an operator + a stale CI-adjacent process) run `terraform apply` at the same time. Given deployment is entirely manual/local (no CI gate — see TF-14), this risk is realistic rather than theoretical.
- **Recommendation:** Add locking. The installed Terraform is v1.15.7, which supports S3 native locking (`use_lockfile = true`, GA since 1.10) without needing a separate DynamoDB table — the lowest-effort fix. Add it to all 6 `backend "s3"` blocks.
- **Alternative solution:** (a) `use_lockfile = true` in each `backend "s3"` block — pros: no new resource, minimal Terraform-only change; cons: requires `terraform init -reconfigure` on next apply per module, and older Terraform CLIs (<1.10) on a teammate's machine won't honor it. (b) Classic DynamoDB lock table (one shared table, added to `bootstrap` module, referenced via `dynamodb_table` in each backend block) — pros: works on any Terraform ≥0.9, well-understood; cons: extra resource to manage/pay for (trivial cost), one more manual bootstrap step. Given `required_version >= 1.6.0` is set repo-wide but the team's actual CLI is 1.15.7, option (a) is recommended as primary with the version constraint bumped to `>= 1.10.0` to enforce it. Effort: S. Cross-pillar: Reliability (prevents state corruption outages), Operational Excellence.

### [Medium] TF-F2 — `terraform fmt` not clean (cosmetic alignment diff in `ingestion/main.tf`)
- **Evidence:** `documentation/terraform/ingestion/main.tf:82-86,144-148` (working tree) — `Sid`/`Effect`/`Action` misaligned vs. `Resource`/`Condition` in the `RateLimitQuery` and `InvokeRuntimeScoped` IAM statement blocks; confirmed by `_context/scans/terraform-fmt.txt` (`terraform fmt -check -recursive -diff` run by orchestrator).
- **Impact:** Purely cosmetic (no functional/semantic difference) but signals the pre-commit/local workflow doesn't run `terraform fmt` before commit, and there is no CI gate to catch it (see TF-14).
- **Recommendation:** Run `terraform fmt -recursive documentation/terraform/` and commit; add a pre-commit hook or CI step to prevent recurrence.
- **Alternative solution:** None needed beyond running `terraform fmt` — trivial, effort: XS.

### [Medium] TF-F3 — No CI pipeline for IaC checks (fmt/validate/plan/lint); fully manual, local deployment
- **Evidence:** No `.github/workflows/`, no CI config found anywhere in the repo (`find` for `*.yml`/`*.yaml` and `.github/` returned nothing); `documentation/README.md` describes a manual `terraform init && apply` runbook per module in a fixed order; `_context/inventory.md` §5 corroborates ("Deployment is manual per README... E2E 'Phase 4 — industrialisation CI' explicitly marked 'à faire'").
- **Impact:** No automated `fmt`/`validate`/`plan`/lint gate means drift, cosmetic issues (TF-F2), and — combined with TF-F1 — concurrent-apply risk are only caught by discipline, not tooling. This is the same underlying gap the prior audit (`audit/20260720-000000/08-terraform.md`) flagged as "manual/hard-coded deployment" — independently re-verified here and confirmed still present.
- **Recommendation:** Add a minimal CI workflow (even just `terraform fmt -check` + `terraform validate -backend=false` per module on PR) before scaling beyond a single operator. This is explicitly already on the project's own roadmap ("Phase 4 — industrialisation CI").
- **Alternative solution:** GitHub Actions matrix job over the 7 module dirs running `fmt -check` + `validate -backend=false`, optionally `tflint`/`checkov` (neither currently installed/configured per the tool-availability probe). Pros: catches formatting/syntax/lint issues pre-merge, cheap to add given GitHub Actions is already the natural CI given GitHub App integration. Cons: `plan`/`apply` automation would need care around the manual secret-injection step (`put-secret-value`) and ordered multi-module dependency chain — recommend starting read-only (fmt/validate/lint only), not auto-apply. Effort: S-M. Cross-pillar: Operational Excellence.

### [Low] TF-F4 — No `validation` blocks on any variable
- **Evidence:** `grep -rn "validation {"` across all `.tf` files under `documentation/terraform/` → zero matches. Example candidates: `environment` (free-form string, e.g. `documentation/terraform/security/variables.tf:11-14`), `aws_region` (free-form string, e.g. `documentation/terraform/ecr/variables.tf:1-4`), `max_runs_per_repo`/`rate_window_seconds` (unbounded numbers, `documentation/terraform/ingestion/variables.tf:64-73`).
- **Impact:** Low — this is a single-environment POC with a small operator set, so the practical blast radius of a malformed var is small, but a typo'd region or negative timeout would only surface as a late `apply`-time provider error rather than an immediate, clear Terraform-time message.
- **Recommendation:** Add lightweight `validation` blocks on the highest-value variables (`aws_region` regex, `environment` allowed-values list, numeric lower bounds on timeouts/thresholds).
- **Alternative solution:** None — additive, low-risk change. Effort: XS.

### [Low] TF-F5 — No `prevent_destroy` on stateful/critical resources
- **Evidence:** `grep -n "prevent_destroy"` across the repo → zero matches. The Terraform state bucket (`documentation/terraform/bootstrap/main.tf:31-33`), the idempotency DynamoDB table (`documentation/terraform/security/main.tf:57-78`), and the two Secrets Manager secrets (`documentation/terraform/security/main.tf:15-51`) have no `prevent_destroy` guard.
- **Impact:** An accidental `terraform destroy` or a resource-replacement plan targeting these would delete the Terraform state bucket itself or the idempotency table with no built-in Terraform-level safety net (S3 versioning on the state bucket mitigates the former partially).
- **Recommendation:** Add `lifecycle { prevent_destroy = true }` to `aws_s3_bucket.state` (bootstrap), `aws_dynamodb_table.idempotency`, and the two `aws_secretsmanager_secret` resources.
- **Alternative solution:** None — purely additive safety guard, effort: XS. Note: this is a deliberate, easy win the project's own existing `lifecycle`/`precondition` discipline (see Strengths) makes natural to extend.

## Notes & assumptions
- `terraform validate` was not executed against any of the 7 modules this session (would require `terraform init -backend=false` per module and was out of scope per the shared context pack's time-boxing); `terraform fmt -check -recursive -diff` results were reused from the context pack (`_context/scans/terraform-fmt.txt`) rather than re-run, per orchestrator instruction.
- `live_aws` is OFF — no AWS API calls were made; all findings are static-analysis-only. In particular, whether S3 bucket versioning (mitigating factor for TF-F5's state-bucket risk) is actually functioning, and whether any drift exists between deployed infra and this code, could not be verified live.
- The prior audit run (`audit/20260720-000000/08-terraform.md`, score 76/100, High finding "manual/hard-coded deployment") was independently re-verified rather than trusted: the "manual deployment, no CI" claim holds (re-confirmed as TF-F3), and the "hard-coded" concern was refined here into two distinct, separately-scored issues — the backend-block account-ID hardcoding (TF-07, judged Partial/unavoidable-by-language-design rather than a straightforward defect) and the absent state-locking (TF-F1, newly identified as the more material High-severity gap, not explicitly called out in the prior run).
- The account-id-in-backend-block "hardcoding" flagged in the task brief was investigated in depth: it is copy-pasted 6× (Terraform backend blocks fundamentally cannot interpolate variables/data sources — a language-level constraint, not a team oversight), and the team has already documented this limitation and the `-backend-config` workaround in `shared.tfvars`. This is scored as Partial (TF-07) rather than treated as a straightforward DRY failure.
- Scoring: 13 of 14 criteria applicable (TF-14 excluded as N/A — no pipeline exists); weighted score = 100 × Σ(credit×weight)/Σ(weight) over the 13 applicable criteria (Σweight=15.0, Σcredit×weight=11.5) = 76.67 → 77.
