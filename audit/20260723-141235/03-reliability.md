This means SQS treats the whole batch as successfully processed and **deletes the permanently-failed message** — it never reaches the DLQ either. The `AccessDeniedException` incident would therefore have produced *zero* DLQ evidence and *zero* alarm signal; only a single CloudWatch log line ("Message abandonné (permanent)") would exist. This is a stronger version of the gap the context pack flagged, found via reading the actual code rather than inferred from the incident description.
3. `var.alarm_actions` still defaults to `[]` and no `aws_sns_topic` exists anywhere in the repo (`terraform/observability/variables.tf:21-25`, repo-wide search) — even the alarms that *do* exist have no notification path.

## Weaknesses / Findings

### [Critical] REL-F1 — No alarm covers a full silent pipeline stall (the exact failure mode that already happened in production)
- **Evidence:** `documentation/terraform/observability/main.tf:24-70` (only `dlq_not_empty`, `worker_errors`, `webhook_errors` alarms exist — none monitor the **main** queue's depth/age); `documentation/terraform/ingestion/main.tf:238-247` (event source mapping has no `function_response_types = ["ReportBatchItemFailures"]`); `documentation/terraform/observability/variables.tf:21-25` (`alarm_actions` defaults to `[]`); repo-wide search found no `aws_sns_topic` anywhere.
- **Impact:** This is not hypothetical — per the context pack, this exact scenario occurred in deployed production: the SQS→worker event-source-mapping poller failed silently (missing `sqs:GetQueueAttributes`), messages piled up in the main queue with zero throughput, and nothing surfaced until CloudWatch Logs were manually inspected. None of the three existing alarms would fire in this scenario: worker `Errors`/`Invocations` stay at zero (the Lambda is never even invoked), and messages never reach the DLQ (the poller never attempts delivery, so `maxReceiveCount` never increments). Even if an alarm did fire, `alarm_actions=[]` means no one would be notified. A recurrence of any cause of poller failure (not just this specific IAM bug) would be equally invisible today.
- **Recommendation:** Add a CloudWatch alarm on the **main** queue's `ApproximateAgeOfOldestMessage` (and/or `ApproximateNumberOfMessagesVisible` sustained > 0 while worker `Invocations` == 0), and wire `var.alarm_actions` to a real SNS topic with a subscription (email/Slack/PagerDuty).
- **Alternative solution:** Composite alarm (queue non-empty AND worker invocations flat over N periods) for precise diagnosis — pros: directly matches the failure signature, low false-positive rate; cons: more complex to author/test, effort M. Simpler alternative: a single `ApproximateAgeOfOldestMessage` threshold alarm on the main queue — pros: simple, effort S, also catches slow/backlogged processing unrelated to this specific bug; cons: less diagnostic specificity. Cross-pillar impact: Operational Excellence (on-call/alerting ownership), and this reuses the same `alarm_actions=[]` gap the Security pillar's prior run flagged adjacent to `SEC-10`.

### [High] REL-F2 — Permanent worker errors are dropped without ever reaching the DLQ, and without incrementing any monitored metric
- **Evidence:** `documentation/scripts/lambdas/worker-dispatcher/handler.py:80-96` — `PermanentError` is caught per-record inside the loop and not re-raised; the `failed` counter is initialized but never incremented anywhere in the function. `documentation/terraform/ingestion/main.tf:238-247` — the event source mapping has no `ReportBatchItemFailures`, so returning normally (as the handler always does after absorbing a `PermanentError`) tells SQS the **entire batch** succeeded, and SQS deletes the message — it never reaches the DLQ.
- **Impact:** The `AccessDeniedException` incident is direct proof of this: it was correctly classified as permanent ("Erreur permanente (%s) — pas de rejeu", `handler.py:76`), which is good hygiene against pointless retries, but the practical side effect is that the corresponding GitHub event was silently discarded — no DLQ entry to inspect, no `worker_errors` alarm triggered (the Lambda invocation itself returns success), and no feedback of any kind to the PR author. The only trace is one CloudWatch log line, easy to miss without actively searching for it.
- **Recommendation:** Either (a) enable `ReportBatchItemFailures` on the event source mapping and have permanent errors reported as batch item failures too (routing them to the DLQ after `maxReceiveCount`, distinct from a blind retry loop), or (b) explicitly `sqs:SendMessage` the payload to the DLQ before dropping it, and/or emit a custom EMF metric (e.g., `PermanentErrors`) with its own alarm so drops are counted and visible.
- **Alternative solution:** Option A — EMF metric + alarm on permanent-error count: pros minimal code change (S effort), no retry-storm risk; cons message payload itself still isn't preserved for replay. Option B — explicit `send_message` to the DLQ on `PermanentError`: pros preserves the message for manual inspection/redrive; cons needs one more IAM action (`sqs:SendMessage` on the DLQ) and slightly more code (M effort). Cross-pillar impact: Operational Excellence (observability gap), Security (Option B is a small least-privilege addition, easy to under- or over-scope — exactly the class of change that caused this pillar's other findings, so should be paired with a smoke test per REL-F3).

### [High] REL-F3 — No blast-radius containment or safe-change mechanism for the single shared worker IAM role / runtime deployment
- **Evidence:** `documentation/terraform/ingestion/main.tf:112-169` — one `aws_iam_role.worker` / one policy document is used for 100% of async traffic across all repos; the inline comments at `main.tf:139-148` and `main.tf:150-165` document, in the maintainers' own words, that two prior "least-privilege tightening" commits (SEC-03, SEC-04) each independently broke this exact role and silently halted the entire pipeline. `documentation/terraform/runtime/main.tf:10-11` — the AgentCore runtime is updated **in place** by digest ("un nouveau build met à jour le runtime en place"), no canary/weighted rollout. Repo-wide search found no `aws_lambda_alias`, CodeDeploy, or any weighted-traffic construct anywhere under `documentation/terraform/`.
- **Impact:** Every change to the worker's IAM policy or the runtime container is instantly 100% live for all traffic, with no staged rollout and no automated pre-promotion check. Combined with REL-F1 (no alarm catches a full stall) and REL-F2 (permanent failures leave no trail), an IAM or config regression can silently take down the entire pipeline for an unbounded period — which is exactly what happened twice.
- **Recommendation:** At minimum, add an automated post-apply smoke test for the `ingestion` module: after `terraform apply`, synchronously invoke the worker Lambda with a synthetic SQS event under the real deployed IAM role and assert success (this mirrors, in automated form, the manual live-testing session that actually found both bugs). Longer-term, consider staged rollout (Lambda alias + traffic shifting) for the worker function.
- **Alternative solution:** Option A — Lambda alias + CodeDeploy weighted traffic shift with automatic rollback on the `worker_errors` alarm: pros, standard AWS blue/green pattern; cons, doesn't cover the SQS-poller-specific failure mode (that's an infra/IAM issue invisible to code-level canary metrics), added complexity for a POC-scale project, effort L. Option B — scripted post-apply smoke invocation (real IAM role, synthetic message, assert `invoke_agent_runtime`/`ReceiveMessage` succeed) gating "done": pros, directly targets exactly this failure class, cheap, effort S–M; cons, still not wired into continuous CI (cross-ref Operational Excellence `OPS-F1`, no CI/CD pipeline exists). Cross-pillar impact: Operational Excellence (this is fundamentally a deploy-pipeline gap), Maintainability (regression-coverage gap for this exact bug class).

### [Medium] REL-F4 — Backoff has no jitter; one remote client relies on SDK default timeouts rather than explicit configuration
- **Evidence:** `documentation/scripts/agents/agent-technical-doc/docagent/retry.py:75` — `delay = min(max_delay, base_delay * (2 ** (attempt - 1)))`, purely deterministic exponential backoff, no randomization. `documentation/scripts/lambdas/worker-dispatcher/handler.py:35-37` — `_agentcore_client()` constructs the `bedrock-agentcore` boto3 client with no explicit `Config(connect_timeout=..., read_timeout=...)`, unlike `docagent/analyzer.py:177-178` which does set explicit Bedrock timeouts.
- **Impact:** Lack of jitter means concurrent retries after a shared transient failure (e.g., a Bedrock throttling burst affecting multiple concurrent worker invocations, bounded by `worker_max_concurrency=5`) can re-synchronize and retry in lockstep, mildly amplifying load on the dependency right when it's already degraded. The un-configured AgentCore client timeout is a smaller risk since the Lambda's own 60s timeout (`worker_timeout_seconds` default) bounds worst-case duration, but it means retry/backoff behavior for that specific call path isn't under explicit code control.
- **Recommendation:** Add jitter to `retry_call` (e.g., `delay * random.uniform(0.5, 1.0)`), and pass an explicit `botocore.config.Config(connect_timeout=..., read_timeout=...)` to the `bedrock-agentcore` client for consistency with the Bedrock analyzer client.
- **Alternative solution:** None — this is a low-effort (S), low-risk fix with no meaningful trade-off; implement directly.
