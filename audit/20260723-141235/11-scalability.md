## Charter & scope
Assess the ability to handle growth in load/data/users gracefully: horizontal scaling, statelessness, elasticity, partitioning/sharding, bottleneck avoidance, and load management. Excludes per-request efficiency (Performance Efficiency, pillar 04), failure recovery/redundancy (Reliability, pillar 03), and loose coupling enabling independent scaling (Decoupling, pillar 10) — cross-referenced where relevant.

## Delta since the prior run (audit/20260721-133806/11-scalability.md, score 73/100)
The only scalability-relevant change since the prior run is the new WAF `RateLimitPerIP` rule (`documentation/terraform/ingestion/waf.tf:179-199`, priority 4, `rate_based_statement { limit = 2000, aggregate_key_type = "IP" }`, block action) plus the CloudFront distribution it rides on. This is a new edge-level volumetric control that did not exist at the prior run. Assessed fresh against SCAL-05 and SCAL-08:

- **SCAL-05 (back-pressure / rate limiting / queue buffering):** was already `Met` on SQS+DLQ buffering and per-repo DynamoDB rate limiting. The WAF rule adds a third, independent layer — coarse per-source-IP volumetric protection at the CDN edge, upstream of API Gateway's own throttle (`main.tf:275-278`, 10 rps/20 burst) and the per-repo quota. It does not change the verdict (already `Met`) but materially strengthens the evidence and the defense-in-depth story: a flood from a single IP is now stopped before it reaches API Gateway/Lambda at all, rather than relying solely on the API Gateway throttle and downstream buffering.
- **SCAL-08 (concurrency limits & downstream protection):** was already `Met` on worker Lambda concurrency capping + transient/permanent error classification + internal backoff. The WAF rate limit is a different protection axis (inbound request volume per IP, not concurrent execution/downstream call protection) — it is complementary, not a substitute, so it does not change the verdict but is noted as an additional strength.

Net effect: no verdict changes. Applying the run's rubric formula (`score = 100 * Σ(credit_i × weight_i) / Σ(weight_i)`) to the identical set of verdicts derived here yields 70/100 — close to, but not identical to, the prior run's reported 73/100 (same maturity band, "Defined"); the ~3-point difference reflects independent recomputation against this run's exact criteria grid rather than a real regression, since no criterion's verdict changed. The rule's threshold (2000 req/5min per IP) is deliberately generous — the design comment (`waf.tf:172-178`) explains this is because GitHub webhook deliveries originate from a shared IP pool across many orgs/repos (`https://api.github.com/meta`, `hooks` key), so a tight per-IP limit would risk blocking legitimate multi-tenant traffic. This is a reasoned trade-off, not an oversight, but it also means the rule is a blunt anti-flood backstop rather than a precise per-tenant scaling control (that role is filled by the existing per-repo DynamoDB counter, `handler.py:194-234`).

All other findings and verdicts from the prior run were independently re-verified against the current committed state and remain substantively unchanged (line numbers shifted slightly in `ingestion/main.tf` due to unrelated IAM-comment additions from the SEC-03/SEC-04 bug-fix commits — citations below use current line numbers).

## Strengths
- Ingestion pipeline is decoupled via SQS with a DLQ, providing queue-based load leveling and buffering under burst — _evidence: `documentation/terraform/ingestion/main.tf:6-23`_
- New: three independent, layered back-pressure controls in front of the webhook — CloudFront/WAF per-IP rate limit (2000 req/5min), API Gateway stage throttle (10 rps/20 burst), and a per-repository sliding-window DynamoDB quota — each protecting a different axis (network flood, API surface, per-tenant abuse) — _evidence: `documentation/terraform/ingestion/waf.tf:179-199`, `documentation/terraform/ingestion/main.tf:270-279`, `documentation/scripts/lambdas/webhook-receiver/handler.py:194-234`_
- Agent runtime is explicitly stateless (no AgentCore Memory/Knowledge Base); each run uses a fresh temp workdir and a fresh clone, with idempotency externalized to DynamoDB rather than kept in-process — _evidence: `documentation/scripts/agents/agent-technical-doc/agent.py:17-18`, `documentation/scripts/agents/agent-technical-doc/docagent/orchestrator.py:216`_
- DynamoDB idempotency table uses on-demand capacity (`PAY_PER_REQUEST`) with a high-cardinality partition key (`repo#pr#sha` / `repo#pr#comment_id`), avoiding both capacity planning and hot-partition risk — _evidence: `documentation/terraform/security/main.tf:57-65`, `documentation/scripts/agents/agent-technical-doc/docagent/idempotency.py:1-4`, `documentation/scripts/lambdas/webhook-receiver/handler.py:244` (rate-limit table shares the same on-demand table, key namespaced `ratelimit#...`)_
- Worker Lambda classifies errors as transient vs. permanent and only re-raises transient ones for SQS retry, with an internal exponential-backoff helper for idempotent sub-operations — _evidence: `documentation/scripts/lambdas/worker-dispatcher/handler.py:25-27,71-77,80-93`, `documentation/scripts/agents/agent-technical-doc/docagent/retry.py:53-90`_
- Per-invocation resource caps (`MAX_FILES`, `MAX_TOTAL_BYTES`, `MAX_SELECTED_FILES`) bound memory/context growth regardless of target repo size — _evidence: `documentation/scripts/agents/agent-technical-doc/docagent/config.py:65-68`_

## Weaknesses / Findings
### [Medium] SCAL-F1 — Worker concurrency hard-capped at 5, shared across all repos/PRs
- **Evidence:** `documentation/terraform/ingestion/variables.tf:53-57`, `documentation/terraform/ingestion/main.tf:238-247`
- **Impact:** `worker_max_concurrency` defaults to 5 and is the single system-wide concurrency budget for every allowed repository. As usage grows (more repos in the allowlist, more simultaneous PR activity), messages queue in SQS rather than processing in parallel, inflating latency; sustained bursts beyond capacity risk exhausting `max_receive_count = 2` (`documentation/terraform/ingestion/main.tf:21`) before enough retries occur, landing legitimate work in the DLQ. The new WAF rate limit does not address this — it protects against inbound request floods, not against organic growth in legitimate concurrent PR activity across an expanding repo allowlist.
- **Recommendation:** Treat the value as a tuned/environment-specific parameter (already is, via `var.worker_max_concurrency`), document its relationship to actual AgentCore/Bedrock concurrent-session quotas, and add an alarm on SQS backlog age so capacity increases are made before user-visible delay, not after.
- **Alternative solution:** Raise `maximum_concurrency` incrementally under load testing once Bedrock AgentCore/model quotas are confirmed sufficient; for stronger isolation, shard by repo/org across multiple queues so one busy repo cannot starve others. Pros: removes the single global throttle point. Cons: sharding adds routing/ops complexity. Effort: S (raise value) / M (sharding). Cross-pillar: Cost Optimization (higher concurrency raises Bedrock spend), Reliability (backlog/DLQ behavior).

### [Medium] SCAL-F2 — No monitoring of scaling headroom (Lambda throttles/concurrency, SQS backlog, WAF rate-limit hits)
- **Evidence:** `documentation/terraform/observability/main.tf:24-70` (only `dlq_not_empty`, `worker_errors`, `webhook_errors` alarms defined — no `Throttles`, `ConcurrentExecutions`, SQS `ApproximateAgeOfOldestMessage`/`ApproximateNumberOfMessagesVisible` on the main queue, or WAF `RateLimitPerIP` block-count alarms); `documentation/terraform/ingestion/waf.tf:194-198` (WAF rule emits CloudWatch metrics and logs to `aws_cloudwatch_log_group.waf`, but no alarm consumes either)
- **Impact:** The team has no early warning before hitting AWS Lambda concurrent-execution limits, Bedrock AgentCore session concurrency limits, a growing SQS backlog, or a sustained WAF rate-limit block event (which could indicate either an attack or a legitimate traffic spike being throttled) — these only become visible after failures accumulate in the DLQ or after manually inspecting WAF logs.
- **Recommendation:** Add CloudWatch alarms for Lambda `Throttles`/`ConcurrentExecutions` on both `webhook` and `worker` functions, SQS `ApproximateAgeOfOldestMessage` on the main queue, and a metric alarm on the WAF `RateLimitPerIP` rule's blocked-request count; document known AWS service quotas and current headroom vs. expected peak.
- **Alternative solution:** None — this is a monitoring gap, not an architectural trade-off. Effort: S.

### [Low] SCAL-F3 — No load testing or capacity model beyond design-time reasoning
- **Evidence:** absence of load-test tooling/results — `documentation/scripts/agents/agent-technical-doc/e2e/` contains only `local_run.py`, `smoke_check.py`, `harness.py` (functional/local, not load tests); no `locust`/`k6`/`artillery` config found in the repository.
- **Impact:** Whether `worker_max_concurrency = 5`, the API Gateway throttle (`throttling_burst_limit = 20` / `throttling_rate_limit = 10`, `documentation/terraform/ingestion/main.tf:275-278`), the new WAF per-IP limit (2000/5min), and SQS buffering actually hold up together under realistic concurrent PR-comment bursts is unverified. This gap is corroborated by the context pack's account of two production incidents this cycle (`sqs:GetQueueAttributes` removal silently stalling the SQS→worker poller, and an under-scoped `InvokeAgentRuntime` resource ARN) that were caught only by live end-to-end testing, not by any static check or load/integration test — the same testing gap that would also catch a scaling regression.
- **Recommendation:** Run a synthetic load test simulating N concurrent webhook deliveries end-to-end (CloudFront/WAF → API GW → SQS → worker → AgentCore) to validate the pipeline before widening the repo allowlist or usage volume.
- **Alternative solution:** None — this is a verification exercise, not a design change. Effort: M.

### [Low] SCAL-F4 — Per-run temp working directory is never explicitly cleaned up
- **Evidence:** `documentation/scripts/agents/agent-technical-doc/docagent/orchestrator.py:216` (`tempfile.mkdtemp(prefix="docagent-")`); no matching `shutil.rmtree`/`TemporaryDirectory` cleanup found anywhere in `orchestrator.py`, `agent.py`, or the rest of `docagent/`.
- **Impact:** If the underlying AgentCore compute is reused across multiple invocations/sessions (typical for warm-start optimization in serverless-like platforms), repeated shallow clones accumulate on local disk across runs on the same host — a per-instance state leak that could eventually cause disk-exhaustion failures under sustained throughput, undermining safe instance reuse at scale.
- **Recommendation:** Use `tempfile.TemporaryDirectory()` as a context manager, or add an explicit `shutil.rmtree(wd, ignore_errors=True)` in a `finally` block around the run.
- **Alternative solution:** None — straightforward defensive fix. Effort: S.
