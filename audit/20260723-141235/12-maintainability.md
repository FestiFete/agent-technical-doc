## Weaknesses / Findings

### [Medium] MNT-F1 — No linter, formatter, or type checker configured or enforced anywhere
- **Evidence:** repo-wide search for `pyproject.toml`, `.flake8`, `ruff.toml`, `setup.cfg`, `.pylintrc`, `mypy.ini`, `.pre-commit-config.yaml` under `/Users/g.mirambeau/Development/AWS/agent-technical-doc` returns no matches (re-verified this session); `documentation/scripts/agents/agent-technical-doc/requirements-dev.txt:1-8` lists only `pytest>=8.0`.
- **Impact:** Style/typo/complexity drift is caught only by human review; type hints exist widely but are never statically checked (no `mypy`/`pyright` run), so annotation correctness is unverified.
- **Recommendation:** Add `ruff` (lint + format) and `mypy`/`pyright` with a minimal `pyproject.toml`; run both locally via `pre-commit` and in CI.
- **Alternative solution:** Adopt `ruff check` + `ruff format` + `mypy --strict` on `docagent/` first (Lambdas are tiny, low-churn) — pros: low effort, fast, single dependency, immediate signal on highest-value code; cons: doesn't cover Lambda handlers or Terraform; effort S; cross-pillar impact: supports MNT-03/MNT-12 and, once wired into CI, Operational Excellence.

### [Medium] MNT-F2 — No CI pipeline exists; test suite and formatting are never enforced automatically
- **Evidence:** no `.github/workflows/`, no other CI config found repo-wide (re-verified via `find` this session); `documentation/README.md:159` self-admits "Phase 4 — industrialisation CI : ⏳ à faire".
- **Impact:** 130 passing tests and clean `terraform fmt` are a snapshot of developer diligence, not a guarantee — nothing prevents a future change from breaking tests, reintroducing a formatting drift, or (as separately discussed under Reliability/Operational Excellence) narrowing an IAM permission that only a live/integration check would catch, before it lands on `develop`/`main`.
- **Recommendation:** Add a GitHub Actions workflow that runs `pytest` (both suites), `ruff`, and `terraform fmt -check -recursive` on every PR touching `documentation/**`.
- **Alternative solution:** Minimal single-job GitHub Actions workflow (checkout, setup-python, `pip install -r requirements.txt -r requirements-dev.txt`, `pytest`, `ruff check`) — pros: cheap, fast (~1 min given current suite speed), directly closes the README's own stated gap; cons: doesn't cover Terraform validation/plan or the class of managed-infrastructure IAM regression seen in production (that needs a deploy-time/integration check, see Reliability/OpsExcellence cross-ref); effort S; cross-pillar impact: Operational Excellence (deployment safety), Reliability (regression prevention).

### [Medium] MNT-F3 — Core LLM-analysis module (`analyzer.py`) still has zero test coverage, including its pure/testable functions
- **Evidence:** `documentation/scripts/agents/agent-technical-doc/docagent/analyzer.py:104-121` (`_extract_json` — fence-stripping, brace-scanning JSON extraction from raw LLM text) and `:124-156` (`select_model` — pure cost/complexity-based model selection) have no corresponding test file; repo-wide grep for `analyzer|_extract_json|select_model|BedrockAnalyzer` across `tests/*.py` returns no matches (re-confirmed this session, unchanged since prior run). All other 12 non-trivial `docagent/` modules have direct or clearly-indirect coverage.
- **Impact:** `_extract_json` is the single point of failure translating unstructured LLM output into the structured dict the rest of the pipeline depends on; its edge cases (malformed JSON, missing fences, nested braces, no JSON at all) are unverified. Regressions here would only surface at runtime against a real Bedrock call.
- **Recommendation:** Add `tests/test_analyzer.py` covering `_extract_json` (fenced/unfenced/malformed/absent JSON) and `select_model` (threshold boundaries, override paths) — both pure, no mocking required.
- **Alternative solution:** Unit-test the two pure functions directly (as above) — pros: matches the codebase's existing DI/pure-function testing pattern exactly, effort S, closes the highest-risk gap; cons: `BedrockAnalyzer.analyze`/`_build_agent` (the `strands`/`boto3` wiring) remains untested, mirroring the deliberate no-network-test policy already applied elsewhere; effort S; cross-pillar impact: Reliability (fewer silent parsing failures in production).

### [Low] MNT-F4 — `docagent/__init__.py` `__all__` is stale, listing 8 of 18 modules
- **Evidence:** `documentation/scripts/agents/agent-technical-doc/docagent/__init__.py:10-19` lists only `config, correlation, repo_reader, selection, drawio, doc_builder, github_client, secrets`; the package contains 18 modules including `analyzer, comments, committer, github_auth, idempotency, metrics, orchestrator, paths, payload, retry`, all omitted. Unchanged since prior run.
- **Impact:** Cosmetic/documentation drift only (Python doesn't enforce `__all__` for the direct-submodule-import style actually used here); a new contributor reading `__init__.py` as a module inventory gets a materially incomplete picture.
- **Recommendation:** Update `__all__` to list all current submodules, or drop it.
- **Alternative solution:** None — trivial one-line fix, no alternative needed.

### [Low] MNT-F5 — Dependencies are version-floored (`>=`), not pinned or lock-filed, for the agent runtime
- **Evidence:** `documentation/scripts/agents/agent-technical-doc/requirements.txt:1-9` (`bedrock-agentcore>=0.1.0`, `strands-agents[otel]>=0.1.0`, `boto3>=1.34.0`, `botocore>=1.34.0`, `pyjwt[crypto]>=2.8.0`, `aws-opentelemetry-distro>=0.10.0`); `requirements-dev.txt:8` (`pytest>=8.0`). No `requirements.lock`/`poetry.lock`/`pip-compile` output found in the project tree (only unrelated `.venv` internal lock files exist). Unchanged since prior run.
- **Impact:** Builds are not reproducible — a fresh `pip install` at a different time can silently pull a newer major/minor `strands-agents`/`boto3`, changing behavior without a corresponding code change or review trigger. No Dependabot/Renovate/`pip-audit` found either.
- **Recommendation:** Generate exact-pinned lock files (`pip-compile`) and enable Dependabot/Renovate for `documentation/scripts/**/requirements*.txt`.
- **Alternative solution:** Adopt `pip-tools`' `pip-compile` for a committed, hash-pinned lock file consumed by the Dockerfile — pros: reproducible builds, keeps `requirements.txt` as the human-editable source; cons: adds a regeneration step to the dependency-bump workflow; effort S; cross-pillar impact: Security (supply-chain), Reliability (reproducible deploys).
