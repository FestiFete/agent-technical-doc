## Charter & scope
Assess how loosely components/services depend on each other at runtime and build time: dependency inversion, async/event-driven boundaries, contract stability, and the ability to change/deploy one part without breaking others. Excludes static decomposition/cohesion (Modularity, pillar 09), overall style choice (Architecture, pillar 07), and elastic independent scaling (Scalability, pillar 11).

This re-verification independently re-examined the webhook → SQS → worker → AgentCore chain, the new CloudFront+WAF edge layer's coupling to the origin (`documentation/terraform/ingestion/waf.tf`), the `ORIGIN_VERIFY_SECRET` shared-secret mechanism, the DI-based orchestrator, the shared DynamoDB idempotency table, and the acyclic Terraform `terraform_remote_state` module graph. `docagent/*` application code is unchanged since the prior run per the context pack and was spot-checked, not re-read line-by-line; the `ingestion` module (main.tf permissions fix, waf.tf, providers.tf, outputs.tf, handler.py `verify_origin`) was read in full as the primary delta surface.

## Delta since the prior run (audit/20260721-133806/10-decoupling.md, score 87/100)

Two substantive changes landed since the prior run, both in `documentation/terraform/ingestion/`:

1. **New CloudFront+WAF edge layer in front of the webhook** (`waf.tf`, new file). This adds a new runtime coupling point that didn't exist before: a `random_password.origin_verify` secret, generated once by Terraform, is injected into **both** CloudFront (`aws_cloudfront_distribution.webhook.origin.custom_header`, `waf.tf:235-238`) and the webhook Lambda (`ORIGIN_VERIFY_SECRET` env var, `main.tf:210`). The Lambda's `verify_origin()` (`handler.py:59-73`) checks it first, before HMAC, as a constant-time comparison, and fails open (`return True`) if the secret is empty — a deliberate testability/local-dev accommodation. This is evaluated under DEC-01/DEC-05 below: it is a clean single-source-of-truth injection pattern (both consumers read from the same Terraform resource, not from each other), not a hardcoded cross-reference, but it is a genuine new coupling between the edge (CloudFront) and origin (Lambda) config that didn't exist in the prior run's architecture. Net assessment: neutral-to-positive for DEC-05 (still env-var-injected, not hardcoded), a mild new dependency for DEC-01 (an edge-to-origin secret handshake is an implicit part of the "stable contract" now, on top of HTTP/HMAC) — not severity-worthy on its own.
2. **The two live-verified IAM bugs described in the context pack** (`sqs:GetQueueAttributes` missing on the worker role; `bedrock-agentcore:InvokeAgentRuntime` scoped to only one of two required ARNs) are now fixed in `main.tf:145-148,161-164`, with inline comments explaining why. Independently assessed below (see DEC-F1): this is **not** primarily a synchronous-cascade failure-isolation issue (DEC-06) — nothing cascaded, the webhook kept accepting and queuing messages fine, and the worker/AgentCore call failure (when it did fire) was itself contained by the existing transient/permanent error classification (`worker-dispatcher/handler.py:71-77`). It **is** best characterized as a DEC-04 finding: the AWS Lambda↔SQS event-source-mapping poller is *managed infrastructure* that silently requires an IAM permission (`GetQueueAttributes`) that is invisible in application code and easy to conclude is dead/removable by static code review alone (as the `SEC-04` commit did) — an implicit coupling point outside the explicit webhook/worker/AgentCore contract. It also exposes a secondary, compounding gap relevant to DEC-06/observability: no alarm exists on the **main** queue's backlog/age (only DLQ-not-empty and Lambda-Errors alarms exist, `observability/main.tf:24-70`), so a silently-starved consumer (zero invocations, zero errors, messages piling up in the main queue, not the DLQ) produces no alarm at all — the failure was isolated to the point of being invisible.

The score moved from 87 to 86: DEC-01 stays Met but the new origin-verify handshake is noted as a small, non-penalized addition to the contract surface; DEC-04 stays Partial but with a second documented issue (the managed-polling-infra permission dependency), reflecting the added weight of evidence from the live-verified incident rather than a code regression. DEC-06 remains Met (no synchronous cascade found) but a new Low finding is added for the queue-backlog alarm gap since it's decoupling-adjacent (a consequence of relying on an unbounded, un-alarmed buffer, DEC-09).

## Strengths
- SQS main+DLQ queue decouples webhook ingress from worker processing, with bounded retention (4d/14d), a visibility timeout tuned to the worker timeout, and a redrive policy — _evidence: `documentation/terraform/ingestion/main.tf:6-23`_
- The worker's `InvokeAgentRuntime` call is fire-and-forget from the worker Lambda's perspective; the AgentCore entrypoint validates the payload and does the real work asynchronously — _evidence: `documentation/scripts/lambdas/worker-dispatcher/handler.py:46-77`, `documentation/terraform/ingestion/variables.tf` (worker timeout much shorter than a full doc-gen run)_
- The orchestrator uses explicit dependency injection: `OrchestratorDeps` is a dataclass of injectable `Callable`s, with real implementations wired lazily by `default_deps()` — high-level run logic depends on abstractions, not concretions — _evidence: `documentation/scripts/agents/agent-technical-doc/docagent/orchestrator.py:33-91`_
- The new origin-verify secret is a clean single-source-of-truth injection (one Terraform `random_password` resource feeds both the CloudFront custom header and the Lambda env var — no cross-hardcoding, no manual secret copy-paste) — _evidence: `documentation/terraform/ingestion/waf.tf:37-40,235-238`, `documentation/terraform/ingestion/main.tf:210`_
- The two-Lambda payload contract (webhook→SQS→worker→AgentCore) follows a tolerant-reader pattern: only `repo_full_name`/`pr_number` are required, the rest is optional and re-resolved by the agent via the GitHub API, reducing coupling to exact field presence — _evidence: `documentation/scripts/agents/agent-technical-doc/docagent/payload.py:26-58`, `documentation/scripts/lambdas/worker-dispatcher/handler.py:46-60`_

- The `verify_origin()` shared-secret check has dedicated unit tests covering valid, invalid, and disabled-when-empty cases — _evidence: `documentation/scripts/lambdas/tests/test_webhook_receiver.py:43-55`_

## Weaknesses / Findings

### [Medium] DEC-F1 — AWS-managed SQS event-source-mapping poller is an undocumented, invisible coupling point in the worker's IAM contract
- **Evidence:** `documentation/terraform/ingestion/main.tf:137-148` (comment: `GetQueueAttributes` "n'est jamais appelé par le code applicatif" yet is required by the managed poller infrastructure), context pack §3 (live-verified: removal of this permission by an earlier `SEC-04` commit caused the poller to silently fail — messages queued but the worker was never invoked, no DLQ movement, no error surfaced anywhere until logs were inspected directly)
- **Impact:** The webhook→worker "contract" is not fully expressed in application code or in the message schema — it also depends on IAM permissions consumed by AWS's own internal SQS-polling control plane, invisible to both static code review and to the two application components themselves. A future least-privilege tightening pass (exactly the kind this repo already did once, `SEC-04`) can silently break the async pipeline again, because nothing in the code, tests, or (at the time) alarms would catch it — the failure mode is "queue grows, nothing consumes it, no error anywhere." This is a hidden coupling to managed infrastructure, conceptually the same risk class as a shared-database hidden bus (DEC-04), just expressed via IAM/control-plane semantics rather than data.
- **Recommendation:** Add an inline comment at the IAM statement (already partially done, `main.tf:139-144`) plus a lightweight regression guard: either a CloudWatch alarm on the main queue's `ApproximateAgeOfOldestMessage` (currently absent — see DEC-F2) or a `terraform plan`-time check/README note flagging that `GetQueueAttributes` is required by the SQS-Lambda event source mapping regardless of application code usage, so a future IAM audit doesn't repeat the same mistake without a live-test safety net.
- **Alternative solution:** None required at Medium severity beyond documentation + alarm coverage — the underlying pattern (Lambda SQS event source mapping) is standard AWS architecture; the gap is process/observability, not architectural. Cross-pillar impact: Reliability, Operational Excellence (this is the same incident referenced in those pillars' criteria for change-safety/regression coverage).

### [Low] DEC-F2 — No alarm on main-queue backlog/age; only DLQ and Lambda-error alarms exist
- **Evidence:** `documentation/terraform/observability/main.tf:24-70` (three alarms: `dlq_not_empty` on the DLQ, `worker_errors` and `webhook_errors` on Lambda `Errors` — no alarm on `aws_sqs_queue.main`'s `ApproximateAgeOfOldestMessage` or `ApproximateNumberOfMessagesVisible`), `documentation/terraform/observability/main.tf:110-121` (the main-queue depth is graphed on the dashboard but not alarmed)
- **Impact:** In the exact incident described in DEC-F1, the main queue (not the DLQ) silently accumulated messages with zero worker invocations and zero worker errors — none of the three existing alarms would have fired. Temporal decoupling via a queue (DEC-09) is only safe if consumer lag/backlog is observable; here it's graphed but not alarmed, so a stalled consumer is a silent failure mode by design today, not just historically.
- **Recommendation:** Add a CloudWatch alarm on `aws_sqs_queue.main`'s `ApproximateAgeOfOldestMessage` (a "consumer is stalled" signal, distinct from the existing "there are permanent failures" DLQ alarm), wired to the same `var.alarm_actions` mechanism used by the other three alarms.
- **Alternative solution:** None needed structurally — this is an additive alarm, not an architecture change. Note it shares the pre-existing gap (`var.alarm_actions` defaults to `[]`, no SNS topic wired anywhere per the context pack) so even a new alarm would currently have nowhere to notify; that gap is out of this pillar's scope (Operational Excellence) but blocks this recommendation's practical value until resolved there. Effort: S.

### [Medium] DEC-F3 — Shared DynamoDB table used as cross-component state store with no documented key-schema contract
- **Evidence:** `documentation/terraform/security/main.tf:57-58` (single `idempotency` table), `documentation/terraform/ingestion/main.tf:76-92` (webhook role: `PutItem`/`UpdateItem`/`Query`), `documentation/terraform/roles/main.tf:74-75` (agent runtime role: `PutItem`/`DeleteItem`/`GetItem`/`UpdateItem`), `documentation/scripts/agents/agent-technical-doc/docagent/idempotency.py:22-52` (agent writes/deletes key `repo#pr#sha`)
- **Impact:** Two independently deployable components (webhook Lambda, AgentCore runtime) both read/write one physical DynamoDB table with no schema owner or interface boundary — only an informal key-naming convention (`repo#pr#comment_id`/`ratelimit#...` vs `repo#pr#sha`) keeps the two key namespaces from colliding. Unchanged since the prior run; still a real, if low-probability, coupling risk.
- **Recommendation:** Document the shared key-schema contract explicitly, or split into two tables (dedup/idempotency vs. rate-limiting) each scoped to a single owning component's IAM policy.
- **Alternative solution:** Two dedicated tables, one per concern, each with its own least-privilege IAM statement. Pros: clear ownership, smaller blast radius, easier independent schema evolution. Cons: one more resource to manage; negligible extra cost at POC scale. Effort: S. Cross-pillar impact: Security, Modularity (09) — cleaner IAM scoping.

### [Low] DEC-F4 — No explicit contract versioning on the webhook→SQS→worker→AgentCore payload
- **Evidence:** `documentation/scripts/agents/agent-technical-doc/docagent/payload.py:26-58` (`InvocationRequest`, no version field), `documentation/scripts/lambdas/worker-dispatcher/handler.py:55-60` (builds the AgentCore payload dict inline), `documentation/scripts/lambdas/webhook-receiver/handler.py:189` (`MessageBody=json.dumps(message)`, no schema/version tag)
- **Impact:** The three producers/consumers agree on payload shape only by convention. Partially mitigated by the tolerant-reader pattern (only 2 fields required). Unchanged since the prior run.
- **Recommendation:** Add a `schema_version` field to the SQS/AgentCore payloads and validate it on the consuming side.
- **Alternative solution:** Shared payload-schema module (dataclass or JSON Schema) imported/validated by both the Lambdas and the agent package. Pros: fail-fast on drift, self-documenting. Cons: adds a shared-code dependency between two currently-independent codebases; no CI today to run contract tests automatically. Effort: S.

### [Info] DEC-F5 — `ORIGIN_VERIFY_SECRET` fails open when unset, extending the trust boundary implicitly
- **Evidence:** `documentation/scripts/lambdas/webhook-receiver/handler.py:69-70` (`if not secret: return True`), `documentation/terraform/ingestion/main.tf:210` (always set from `random_password.origin_verify.result` in this Terraform config, so the fail-open path is not reachable via this IaC as currently written)
- **Impact:** This is a deliberate, documented design choice (enables running the Lambda locally/in tests without CloudFront in front), and the current Terraform always populates the env var, so it's not exploitable via this codebase today. It is worth flagging as a coupling-contract subtlety: the security posture of the origin now implicitly depends on an operational invariant (the env var must always be set in any real deployment) that lives outside the type system/schema — a future deploy path that omits the variable (e.g. a manual `terraform apply -var` override, a new environment) would silently widen the trust boundary back to "any direct API Gateway caller," with no error, no log distinguishing it from the intended fail-open test path.
- **Recommendation:** Consider a Terraform-level guard (e.g. a `precondition` on the Lambda resource similar to the existing `runtime_arn` precondition at `main.tf:127-130`) that fails the apply if `random_password.origin_verify.result` is empty, making the invariant self-enforcing rather than relying on convention.
- **Alternative solution:** None needed — Info severity, no live exploit path in current code; this is a "keep it that way" flag, not a defect.
