## Charter & scope
Assesses environmental impact of the workload: utilization/scale-to-zero, energy-efficient compute (Graviton/serverless), managed vs self-managed infra, data minimization/retention, algorithmic/processing efficiency, batching vs polling, region choice, storage tiering, idle test/dev environments, and proportionate observability volume. Dollar cost is out of scope (→ Cost Optimization, pillar 05); raw latency/throughput is out of scope (→ Performance Efficiency, pillar 04) — this review looks only at the resource-waste dimension of choices that overlap those pillars.

## Weaknesses / Findings

### [Low] SUS-F1 — Terraform state S3 bucket has versioning enabled with no lifecycle rule to expire noncurrent versions
- **Evidence:** `documentation/terraform/bootstrap/main.tf:36-41` (`aws_s3_bucket_versioning` "Enabled", no accompanying `aws_s3_bucket_lifecycle_configuration` anywhere in `bootstrap/main.tf`)
- **Impact:** Every `terraform apply` across 7 modules adds a new state object version that is retained forever. State files are small, so the absolute waste is negligible, but it is unbounded by design and contradicts the data-minimization pattern applied everywhere else in this repo (SQS/DynamoDB/CW logs/ECR/CloudTrail S3 all have explicit retention limits).
- **Recommendation:** Add an `aws_s3_bucket_lifecycle_configuration` rule that expires noncurrent state versions after e.g. 90 days.
- **Alternative solution:** None — Low severity, effort is trivial (a few lines of HCL), no meaningful cross-pillar trade-off.

### [Low] SUS-F2 — CloudTrail S3 bucket has a bounded expiration but no storage-class transition before deletion
- **Evidence:** `documentation/terraform/observability/cloudtrail.tf:51-63` (`aws_s3_bucket_lifecycle_configuration.cloudtrail` — only an `expiration` block at `var.cloudtrail_s3_retention_days`, default 365 days; no `transition` block to `STANDARD_IA`/`GLACIER`/`INTELLIGENT_TIERING`)
- **Impact:** Unlike the state-bucket gap (SUS-F1, unbounded), this data *is* bounded — it will not accumulate forever. But for a full year, CloudTrail audit logs (rarely read after the first few days, if ever) sit on S3 Standard, the least storage-efficient tier, rather than moving to a colder/cheaper/lower-overhead tier after an initial access window. This is a right-sizing gap (SUS-08), not a data-minimization gap (SUS-04 is otherwise satisfied here).
- **Recommendation:** Add a `transition` block (e.g., to `STANDARD_IA` after 30 days, or `INTELLIGENT_TIERING` which handles this automatically with no code change) ahead of the existing `expiration` at 365 days.
- **Alternative solution:** None — Low severity; trivial HCL addition, no functional or security trade-off (CloudTrail's own log-file-validation and the bucket's encryption/public-access-block are unaffected by storage class).

### [Low] SUS-F3 — Region choice (`eu-central-1`) has no documented sustainability rationale
- **Evidence:** `documentation/terraform/shared.tfvars:14` (`aws_region = "eu-central-1"`, hardcoded and identical across all 7 modules' backends); no mention of carbon/region trade-offs found in `documentation/README.md`
- **Impact:** `eu-central-1` (Frankfurt) is a reasonable EU-resident choice for data-locality/latency reasons, but the repo shows no evidence that sustainability (grid carbon intensity) was weighed against alternative EU regions when the region was picked. This is a low-impact criterion at POC scale and workload is tiny (event-driven, low request volume). Note the new CloudFront/WAFv2 CLOUDFRONT-scope resources are required by AWS to live in `us-east-1` regardless of stack region (`documentation/terraform/ingestion/providers.tf`, `aws.us_east_1` alias) — this is a hard AWS constraint, not a discretionary choice, and does not affect this finding.
- **Recommendation:** If/when the workload scales or a region change is otherwise on the table, document the trade-off between `eu-central-1` and lower-carbon-intensity EU regions as part of that decision; not worth a dedicated migration today given the workload's small footprint.
- **Alternative solution:** None — Low severity; a region migration is disproportionate effort for a POC-scale event-driven workload with no measured environmental impact data to justify it.

### [Info] SUS-F4 — Local E2E smoke-check script polls with a `while True` + `sleep` loop
- **Evidence:** `documentation/scripts/agents/agent-technical-doc/e2e/smoke_check.py:82-93`
- **Impact:** This is a local developer/CI convenience script (not part of deployed infrastructure), so its resource footprint is confined to whoever runs it manually; no production waste. Flagged for completeness only.
- **Recommendation:** No action needed; noted as informational since the pillar charter calls out polling-vs-event-driven patterns specifically.
- **Alternative solution:** None — Info-level, out of production scope.
