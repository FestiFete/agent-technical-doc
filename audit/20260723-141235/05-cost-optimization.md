## Charter & scope
Assess the ability to run at the lowest price point for the required outcome: avoiding waste, right-sizing, pricing-model fit, cost visibility/attribution, and managing spend over time. Excludes raw performance tuning (→ Performance Efficiency) and elastic scaling correctness (→ Scalability).

## Delta since the prior run (audit/20260721-133806/05-cost-optimization.md, score 82/100)

Two genuinely new recurring-cost surfaces landed since the prior run: WAFv2 + CloudFront in front of the webhook (`documentation/terraform/ingestion/waf.tf`) and an account-wide CloudTrail trail + S3 + CloudWatch Logs + GuardDuty detector (`documentation/terraform/observability/cloudtrail.tf`). Both were independently re-checked against this pillar's criteria (not the Security rationale, which is out of scope here):

- **WAFv2 WebACL** (`documentation/terraform/ingestion/waf.tf:56-206`): scope=CLOUDFRONT, 4 rules (1 custom size-constraint, 1 custom rate-limit, 2 AWS-managed rule groups). This is a small **flat monthly base fee regardless of traffic** (WebACL + per-rule + per-managed-rule-group charges, plus a low per-million-request fee) — it does not scale to zero at idle, unlike the rest of the stack. It is deliberately minimal: only 2 managed rule groups (not the full AWS managed rule catalogue), one already partially overridden to `Count` to avoid false positives (`waf.tf:134-139`), and the rate-limit threshold is generously calibrated to GitHub's shared webhook IP pool rather than over-engineered (`waf.tf:172-178`). Logging retention reuses the existing shared `var.log_retention_days` (14d default, `waf.tf:53`, `documentation/terraform/ingestion/variables.tf:65-69`) rather than introducing a new unbounded log stream.
- **CloudFront distribution** (`waf.tf:214-263`): `price_class = "PriceClass_100"` (cheapest tier, US/Canada/Europe edge locations only, `waf.tf:218`) — a deliberate cost-conscious choice given the origin (GitHub webhooks) has no need for global edge presence. Caching is disabled (`cache_policy_id` = Managed-CachingDisabled, `waf.tf:250`) — this is a correctness requirement (raw body needed for HMAC verification), not a cost oversight, and has negligible cost impact since this is a low-volume webhook endpoint already throttled at the API Gateway stage (10 rps / 20 burst, carried over unchanged). No CloudFront standard access logging to S3 was added (no extra S3 storage cost).
- **CloudTrail + S3 + CloudWatch Logs** (`documentation/terraform/observability/cloudtrail.tf`): S3 lifecycle expiration is present and bounded (`cloudtrail.tf:51-63`, default 365 days — `documentation/terraform/observability/variables.tf:58-62`), longer than the 14-day application-log default but explicitly justified in-line as a security/audit-log retention need (`cloudtrail.tf:14-16`), which is reasonable industry practice for an audit trail rather than waste. CloudWatch Logs retention is likewise explicitly bounded (90 days, `cloudtrail.tf:103-107`, default at `variables.tf:52-56`) rather than left unset (which would default to "never expire"). Server-side encryption uses the S3-managed key (`aws:kms` via S3, not a CMK) — a deliberate, documented cost/permissions trade-off consistent with an existing project-wide constraint (`cloudtrail.tf:14-16`, cross-referenced to `SEC-07`), not a new gap.
- **GuardDuty detector** (`cloudtrail.tf:221-224`): bare `enable = true`, no optional paid features (S3 Protection, EKS Runtime Monitoring, Malware Protection, RDS Protection) enabled — the cheapest viable configuration. Combined with the architecture's continued absence of any VPC (`grep -rn "aws_vpc|vpc_config" documentation/terraform/` → no matches), GuardDuty has no VPC Flow Logs to analyze, further bounding its usage-based cost to CloudTrail management-event analysis only.
- Both new account-wide controls are individually toggleable (`enable_cloudtrail` / `enable_guardduty`, default `true`, `documentation/terraform/observability/variables.tf:40-49`) specifically to avoid duplicate cost if an organization-level trail/detector already exists — a cost-aware design choice called out explicitly in comments (`cloudtrail.tf:6-12`).
- Tagging (`Project`/`Env`/`Module`) was correctly extended to the **new `aws.us_east_1` provider alias** required for the CLOUDFRONT-scope WAFv2 resources (`documentation/terraform/ingestion/providers.tf:41-51`), so cost-allocation-tag coverage did not regress with the new region touchpoint.

**Net assessment:** both additions are reasonably bounded and justified — no unbounded/runaway spend risk was found. The one real effect on this pillar's scoring is that **COST-06 (budgets/alerts)** remains Missing while the number of independent recurring-cost line items has grown (Lambda/DynamoDB/SQS/API Gateway/Bedrock, now plus WAF/CloudFront and CloudTrail/S3/CloudWatch/GuardDuty) — the case for a monthly budget guardrail is modestly stronger than at the prior run, though total spend is still expected to remain low at POC scale. All other criteria verdicts are reconfirmed unchanged from the prior run's independent re-check.

## Weaknesses / Findings

### [Medium] COST-F1 — No AWS Budgets or Cost Anomaly Detection configured
- **Evidence:** `grep -rln "aws_budgets|aws_ce_|budgets_budget|anomaly" documentation/terraform/ documentation/scripts/` returns no matches (absence re-verified this run)
- **Impact:** No proactive dollar-denominated alert exists across the now-larger set of independent recurring-cost line items (Lambda, DynamoDB, SQS, API Gateway, Bedrock, plus the new WAFv2/CloudFront and CloudTrail/S3/CloudWatch/GuardDuty). Cost visibility remains entirely reactive (monthly bill review); the per-repo run quota and API Gateway throttle are indirect ceilings on request/invocation volume, not on dollars.
- **Recommendation:** Add an `aws_budgets_budget` (monthly cost budget, SNS-notified thresholds at 50%/80%/100%) and/or AWS Cost Anomaly Detection scoped to the `Project=agent-technical-doc` cost-allocation tag already applied consistently across all 7 modules. Both are free AWS features.
- **Alternative solution:** None needed — pure addition, no trade-off. Effort: S (fits naturally into the existing `observability` module, which already centralizes alarms and now also owns CloudTrail/GuardDuty).

### [Low] COST-F2 — No CloudWatch metric/log ingestion cost control beyond retention (no sampling, no log-level tuning)
- **Evidence:** No `OTEL_TRACES_SAMPLER` or equivalent sampling config found (`grep -rn "sampling|OTEL_TRACES_SAMPLER" documentation/` → no matches); WAF logging configuration has no `logging_filter` block, so it logs all matched requests, not a sample (`documentation/terraform/ingestion/waf.tf:208-212`)
- **Impact:** At current POC volume this is negligible — WAF log volume is bounded indirectly by the unchanged API Gateway throttle (10 rps / 20 burst), and CloudTrail/observability log volume is bounded by retention (14d app logs, 90d CloudTrail logs) rather than by sampling. Log/trace volume still scales linearly with traffic with no sampling ceiling, so this is not structurally bounded independent of growth.
- **Recommendation:** If run/request volume grows materially, consider trace sampling (`OTEL_TRACES_SAMPLER=parentbased_traceidratio` at 10-20%) and/or a WAF logging filter to exclude `ALLOW`-action noise while keeping `BLOCK`/`COUNT` events.
- **Alternative solution:** None — low priority at current scale; forward-looking guardrail. Effort: S.

### [Low] COST-F3 — No dedicated ephemeral/non-prod environment lifecycle (single POC environment only)
- **Evidence:** `documentation/terraform/shared.tfvars` (`environment = "POC"`, single value across all modules); no second `tfvars` set or workspace found
- **Impact:** COST-03 and COST-09 are not directly demonstrable because there is no separate non-prod environment to observe being torn down/scheduled — the single environment already happens to be fully scale-to-zero by construction for the compute-layer resources, though the new WAFv2 WebACL and CloudTrail trail carry small flat monthly base fees that do not scale to zero regardless of environment count.
- **Recommendation:** If/when a second environment is introduced, document or automate its teardown, and re-evaluate whether the WAF/CloudTrail/GuardDuty controls should be shared account-wide (as currently designed, via the `enable_cloudtrail`/`enable_guardduty` toggles) rather than duplicated per environment.
- **Alternative solution:** None — current single-environment, fully-serverless-by-default design sidesteps the need for explicit non-prod scheduling. Effort: N/A (informational).
