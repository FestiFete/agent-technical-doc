The prior run's 98/100 was independently re-checked, not carried forward, per the context pack's instruction. Two of its "Met" verdicts do not hold against the current committed state (`f89ea51`), which is why the score moves down to 83/100 (maturity 4, down from 5):

1. **ARC-08 (design documented and matches code): downgraded Met → Partial.** The prior report explicitly verified `documentation/ARCHITECTURE.md` "matches the current on-disk code and Terraform almost exactly" — but that check predates the CloudFront+WAF+origin-verify edge layer (`documentation/terraform/ingestion/waf.tf`, all 263 lines new). `ARCHITECTURE.md`'s Section 1 diagram, component inventory (Section 3), and "Invariants clés" (Section 4) still show GitHub → API Gateway as the direct, sole entry point, with zero mention of CloudFront, WAFv2, or the `X-Origin-Verify` anti-bypass mechanism — confirmed by a direct grep of the file (no hits for "CloudFront"/"WAF"). This is not a minor omission: the edge layer is now the internet-facing front door of the whole system and closes a previously-open gap (`SEC-F1`) that the architecture doc's own "invariants" section would be the natural place to record, alongside the existing ones ("l'agent ne touche jamais SQS", "le webhook n'a pas le token GitHub").
2. **ARC-10 (failure domains intentional): downgraded Met → Partial.** The context pack documents a real incident: `sqs:GetQueueAttributes` was removed from the worker role by an earlier least-privilege commit (`SEC-04`), which silently broke the Lambda-managed SQS event-source-mapping poller — 100% of async processing stopped with messages piling up in the main queue, **and no alarm fired**, because the only SQS alarm in the repo watches the DLQ (`documentation/terraform/observability/main.tf:24-38`), not the main queue, and the only Lambda alarms watch the `Errors` metric (`main.tf:41-70`), which stays at zero when the poller can't even invoke the function. The main queue's `ApproximateNumberOfMessagesVisible` appears only in the dashboard (`main.tf:117`), never in an `aws_cloudwatch_metric_alarm`. The single-queue/single-worker-role design is a reasonable, deliberate blast-radius choice at POC scale, but the fact that its most likely failure mode (IAM regression on the shared managed-infrastructure permission) has no detection path at all — compounded by `alarm_actions` defaulting to `[]` with no SNS topic anywhere (`documentation/terraform/observability/variables.tf:21-25`) — means the "boundaries are intentional" bar is only half met: the isolation exists, but the operational visibility into that isolation's failure does not.

Everything else re-verified holds: the event-driven pipeline shape, component responsibilities, idempotency/consistency strategy, statelessness, async invocation pattern, and extensibility pattern (new agents via `agents.json`, new edge layer added without touching the core Lambda pipeline) are all still accurate and, if anything, the CloudFront+WAF addition is itself good evidence *for* ARC-12 (extensibility without redesign) and ARC-09 (justified, not accidental, complexity — `waf.tf:1-29` documents in comments exactly why CloudFront-in-front-of-HTTP-API is required, not a gratuitous addition). The two previously-flagged findings (`ARC-F1` rate-limit IAM/code mismatch, `ARC-F2` single-table multiplexing) remain unresolved and are carried forward unchanged.

## Weaknesses / Findings

### [Medium] ARC-F3 — ARCHITECTURE.md does not document the new CloudFront+WAF+origin-verify edge layer
- **Evidence:** `documentation/ARCHITECTURE.md:1-160` (no mention of CloudFront/WAF/origin-verify anywhere — confirmed via grep) vs. `documentation/terraform/ingestion/waf.tf:1-263` (new `aws_wafv2_web_acl`, `aws_cloudfront_distribution`, `random_password.origin_verify`) and `documentation/terraform/ingestion/outputs.tf:1-9` (the GitHub-configured `webhook_url` now points at CloudFront, not API Gateway). `documentation/AUDIT.md:13,19,52,76,124,142` also still lists "WAF absent" as an open gap, unchanged.
- **Impact:** `ARCHITECTURE.md` is the repo's stated single source of truth for the end-to-end flow (it is cross-referenced from `AUDIT.md` and is the artifact a new engineer or a future security reviewer would read first). It currently omits the system's actual internet-facing entry point and the anti-bypass invariant that closes the "direct API Gateway URL" gap — a reader relying on it would materially misunderstand the trust boundary (e.g. might believe API Gateway is still directly reachable without a secondary check, or might not realize WAF logging/rate-limiting exists at all). `AUDIT.md` actively contradicts current state by still listing WAF as a missing gap.
- **Recommendation:** Add CloudFront + WAFv2 + the origin-verify header check to the Section 1 Mermaid diagram, add a row to the Section 3 component inventory, and add the anti-bypass check as a fifth bullet under Section 4 "Invariants clés" (alongside the existing four). Update `AUDIT.md`'s security scoreline and open-gaps list to reflect WAF as delivered.
- **Alternative solution:** None — this is a documentation-update task, not a design alternative. Cross-reference: Documentation-fidelity finding also relevant to Maintainability (09/onboarding) but scoped here since ARC-08 explicitly charters "matches the code."

### [Medium] ARC-F4 — No alarm covers the exact failure signature of the SQS-poller IAM incident (main-queue growth with zero worker throughput)
- **Evidence:** `documentation/terraform/observability/main.tf:24-38` (`dlq_not_empty` alarms only on the DLQ's `ApproximateNumberOfMessagesVisible`), `main.tf:41-54` (`worker_errors` alarms only on the `Errors` metric, which stays at zero when the Lambda is never invoked), `main.tf:117` (the main queue's `ApproximateNumberOfMessagesVisible` exists only as a dashboard widget, never as an `aws_cloudwatch_metric_alarm` resource); `documentation/terraform/observability/variables.tf:21-25` (`alarm_actions` defaults to `[]`, no SNS topic exists in the repo, so even the alarms that do exist have no notification path).
- **Impact:** The context pack documents that this exact scenario already happened live: a worker-role IAM regression (missing `sqs:GetQueueAttributes`) silently stopped 100% of async processing, with messages accumulating in the main queue and zero DLQ movement, undetected until logs were inspected directly. None of the three existing alarms would have caught it (DLQ stayed empty because messages never got far enough to exhaust `maxReceiveCount`; worker `Errors` stayed at zero because the poller itself failed, not the function). This means the architecture's failure-domain design provides isolation (SQS decouples webhook from worker, DLQ isolates permanent failures) but not detectability for the single-shared-role failure mode that is arguably the most likely one in a system that has already had two such IAM regressions land undetected.
- **Recommendation:** Add an alarm on the main queue's `ApproximateNumberOfMessagesVisible` (age-based, e.g. `ApproximateAgeOfOldestMessage` > worker timeout, or a "growing with zero worker invocations" composite alarm) and wire `alarm_actions` to at least one real notification target (this reuses the pre-existing, still-open `OPS-F2` gap noted in the context pack).
- **Alternative solution:** Composite CloudWatch alarm: `ApproximateAgeOfOldestMessage(main queue) > worker_timeout_seconds` AND `Invocations(worker) == 0` over the same period — directly encodes "queue has work, worker isn't running," which the current metric set cannot express. Pros: cheap (no new infra, just alarm config), catches this exact incident class going forward. Cons: still needs a real SNS/notification target to be actionable. Effort: S. Cross-pillar impact: Reliability (03), Operational Excellence (01) — this is primarily an observability/alerting fix; flagged here because it is the concrete evidence that the failure-domain boundary (ARC-10) is not fully backed by intentional detection.

### [Low] ARC-F1 — Dead/mismatched IAM statement for the rate-limit DynamoDB write path (unresolved, carried forward)
- **Evidence:** `documentation/terraform/ingestion/main.tf:82-92` (`RateLimitQuery` statement grants `dynamodb:Query` gated on `LeadingKeys = ["${var.mention_handle}#*"]`) vs. `documentation/scripts/lambdas/webhook-receiver/handler.py:204-216` (`_increment_repo_counter` actually calls `UpdateItem` on keys prefixed `ratelimit#…`, an operation already separately covered by the unconditional `ClaimIdempotency` statement at `documentation/terraform/ingestion/main.tf:76-81`).
- **Impact:** Unchanged since the prior run: the `RateLimitQuery` statement neither authorizes the action the code performs nor matches the key prefix actually used. It is inert; the real rate-limit write path is authorized by the broader `ClaimIdempotency` grant instead. Still a low-severity authorization/implementation drift, not a functional break.
- **Recommendation:** Either implement the rate limiter with a `Query`+condition matching this statement, or remove `RateLimitQuery` and add a correctly-scoped `dynamodb:LeadingKeys = ["ratelimit#*"]` condition to the statement that actually grants `UpdateItem`.
- **Alternative solution:** None — small, self-contained fix. Cross-reference: primarily a Security-pillar (IAM correctness) finding.

### [Info] ARC-F2 — Single DynamoDB table multiplexes three distinct data-ownership domains (unresolved, carried forward)
- **Evidence:** `documentation/terraform/security/main.tf:54-79` (one `idempotency` table, hash key `pk`); consumers: webhook dedup key `repo#pr#comment_id` (`documentation/scripts/lambdas/webhook-receiver/handler.py:272`), webhook rate-limit key `ratelimit#{repo}#{bucket}` (`documentation/scripts/lambdas/webhook-receiver/handler.py:199-201`), agent strong-claim key `repo#pr#sha` (`documentation/scripts/agents/agent-technical-doc/docagent/idempotency.py`).
- **Impact:** Unchanged — three semantically different concerns share one table, distinguished only by key-prefix convention. Workable at current scale, not a correctness risk today.
- **Recommendation:** No immediate action; prefer a dedicated table or a `type` discriminator attribute if a fourth consumer is added.
- **Alternative solution:** None — informational, POC-appropriate as-is.
