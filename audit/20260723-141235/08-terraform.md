## Weaknesses / Findings

### [High] TF-F1 — No state locking configured on any S3 backend (no DynamoDB lock table, no S3 native locking)
- **Evidence:** `documentation/terraform/ecr/providers.tf:11-16`, `documentation/terraform/security/providers.tf:11-16`, `documentation/terraform/roles/providers.tf:11-16`, `documentation/terraform/runtime/providers.tf:15-20`, `documentation/terraform/ingestion/providers.tf:19-24`, `documentation/terraform/observability/providers.tf:11-16` — all 6 S3-backed `backend "s3"` blocks re-inspected this run, none declares `dynamodb_table` or `use_lockfile`. Independently re-confirmed unchanged since the prior audit; no locking was added alongside the new `ingestion/waf.tf` or `observability/cloudtrail.tf` work despite both modules gaining new stateful resources (WAFv2 ACL, CloudFront distribution, CloudTrail trail, GuardDuty detector) in this same period.
- **Impact:** All 6 S3-backed modules can suffer concurrent-apply state corruption if two operators (or a stale process) run `terraform apply` simultaneously. Deployment remains entirely manual/local (no CI gate — TF-F3), so this risk is realistic, not theoretical. The blast radius has grown slightly since the prior run: `ingestion` and `observability` now manage more resources (WAF/CloudFront, CloudTrail/GuardDuty) than before, raising the cost of a corrupted state in those two modules specifically.
- **Recommendation:** Add locking. Installed Terraform is v1.15.7 (confirmed this session), which supports S3 native locking (`use_lockfile = true`, GA since 1.10) without a separate DynamoDB table. Add to all 6 `backend "s3"` blocks and bump `required_version` to `>= 1.10.0` to enforce it.
- **Alternative solution:** (a) `use_lockfile = true` in each `backend "s3"` block — pros: no new resource, minimal change; cons: requires `terraform init -reconfigure` per module next apply, and CLIs <1.10 won't honor it. (b) Classic DynamoDB lock table (one shared table added to `bootstrap`, referenced via `dynamodb_table` in each backend block) — pros: works on any Terraform ≥0.9; cons: one more resource/manual bootstrap step (trivial cost). Recommended: (a), given the team's actual CLI (1.15.7) already exceeds the 1.10 floor. Effort: S. Cross-pillar: Reliability (prevents state corruption outages), Operational Excellence.

### [Medium] TF-F3 — No CI pipeline for IaC checks (fmt/validate/plan/lint); fully manual, local deployment
- **Evidence:** No `.github/workflows/` or any other CI config anywhere in the repo (`find /Users/g.mirambeau/Development/AWS/agent-technical-doc -maxdepth 2 -iname ".github"` → empty, re-run this session). Independently re-confirmed still absent even after the WAF and CloudTrail modules landed.
- **Impact:** No automated `fmt`/`validate`/`plan`/lint gate. This is the same underlying gap that let two of this cycle's regressions (`SEC-03`, `SEC-04` — see context pack §3) ship silently: both were syntactically valid Terraform (so `fmt`/`validate` alone, even if automated, would not have caught them), which specifically argues for at minimum a CI-gated `fmt -check`/`validate` as a floor, with the deeper regression class needing integration testing (already flagged cross-pillar). Combined with TF-F1, concurrent-apply risk is also only caught by discipline, not tooling.
- **Recommendation:** Add a minimal CI workflow (`terraform fmt -check` + `terraform validate -backend=false` per module on PR) as a first, cheap step — explicitly already on the project's own roadmap ("Phase 4 — industrialisation CI" per context pack).
- **Alternative solution:** GitHub Actions matrix job over the 7 module dirs running `fmt -check` + `validate -backend=false`, optionally `tflint`/`checkov` (neither installed/configured — re-confirmed this session, `tflint`/`checkov`/`tfsec`/`trivy` not on `PATH`). Pros: cheap, catches formatting/syntax pre-merge. Cons: won't catch managed-infrastructure permission gaps (the actual root cause of `SEC-03`/`SEC-04`) — that needs integration/live testing, out of this pillar's scope. Effort: S-M. Cross-pillar: Operational Excellence, Reliability.

### [Low] TF-F4 — No `validation` blocks on any variable
- **Evidence:** `grep -rn "validation {"` across all `.tf` files under `documentation/terraform/` (re-run this session, including the 2 new files) → zero matches. New candidates added this cycle: `documentation/terraform/observability/variables.tf:52-67` (`cloudtrail_log_retention_days`, `cloudtrail_s3_retention_days`, `secrets_access_alarm_threshold` — all unbounded numbers).
- **Impact:** Low — single-environment POC, small operator set. A malformed var surfaces as a late `apply`-time error rather than an immediate Terraform-time message.
- **Recommendation:** Add lightweight `validation` blocks on the highest-value variables (numeric lower bounds on retention/threshold variables, `aws_region` regex, `environment` allowed-values list).
- **Alternative solution:** None — additive, low-risk change. Effort: XS.

### [Low] TF-F5 — No `prevent_destroy` on stateful/critical resources
- **Evidence:** `grep -n "prevent_destroy"` across the repo (re-run this session) → zero matches, including on the two new stateful resources added this cycle: the CloudTrail S3 bucket (`documentation/terraform/observability/cloudtrail.tf:26-29`) and the CloudTrail trail itself (`documentation/terraform/observability/cloudtrail.tf:144-156`), neither of which has a `lifecycle { prevent_destroy = true }` guard. Also still absent on the pre-existing state bucket (`documentation/terraform/bootstrap/main.tf:32-34`), idempotency table, and both Secrets Manager secrets (`documentation/terraform/security/main.tf`).
- **Impact:** An accidental `terraform destroy` or replacement plan against these resources has no Terraform-level safety net. The CloudTrail trail/bucket are now included in this exposure, widening the finding's scope slightly versus the prior run.
- **Recommendation:** Add `lifecycle { prevent_destroy = true }` to `aws_s3_bucket.state` (bootstrap), `aws_dynamodb_table.idempotency`, both `aws_secretsmanager_secret` resources, and now `aws_s3_bucket.cloudtrail`/`aws_cloudtrail.account`.
- **Alternative solution:** None — purely additive safety guard. Effort: XS.
