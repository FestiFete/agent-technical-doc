## Charter & scope
Assesses the workload's ability to perform correctly and consistently and to recover from failures: fault tolerance / redundancy, RTO/RPO & backups, idempotency, retries/timeouts, dead-letter/failure isolation, graceful degradation, health-driven recovery, quota/throttling handling, safe change management, durable state, failure-mode testing, and dependency blast-radius containment. Load-growth/elasticity is **Scalability (11)**, throughput/latency is **Performance Efficiency (04)**, and CI/CD pipeline mechanics are **Operational Excellence (01)** — this pillar covers only the *outcomes* of change safety (rollback / canary / reversibility).

Static audit (`live_aws=OFF`): every verdict is derived by reading the committed code/IaC; runtime-only facts (effective encryption, live alarm state) are judged on IaC. Grounded in the AWS Well-Architected Reliability pillar ([AWS Config reliability best-practices](https://docs.aws.amazon.com/config/latest/developerguide/operational-best-practices-for-wa-Reliability-Pillar.html)) and the Lambda–SQS partial-batch-response guidance ([Lambda SQS batch item failures](https://docs.aws.amazon.com/lambda/latest/dg/services-sqs-errorhandling.html)). Content rephrased for licensing compliance.

## Weaknesses / Findings

### [Critical] REL-F1 — No alarm can detect a full silent pipeline stall
- **Evidence:** `documentation/terraform/observability/main.tf:24-70` — the only three alarms are DLQ depth, worker `Errors`, and webhook `Errors`; none monitor the **main** queue's `ApproximateAgeOfOldestMessage`/depth. `documentation/terraform/ingestion/main.tf:238-247` — the event source mapping has no `function_response_types = ["ReportBatchItemFailures"]`. `documentation/terraform/observability/variables.tf:21-25` — `alarm_actions` defaults to `[]`; a repo-wide search finds no `aws_sns_topic`.
- **Impact:** If the managed SQS→worker poller stops (e.g. loss of `sqs:GetQueueAttributes`, an IAM class the maintainers' own comment at `ingestion/main.tf:139-147` documents as having previously broken it), messages accumulate in the main queue with zero throughput. Worker `Errors`/`Invocations` stay flat (the function is never invoked) and nothing reaches the DLQ (the poller never delivers, so `maxReceiveCount` never increments) — so none of the three alarms fire. Even if one did, `alarm_actions=[]` means no notification. This is a data-processing outage that is structurally invisible to the current monitoring, matching the failure mode the context pack reports actually occurred in production.
- **Recommendation:** Add a CloudWatch alarm on the **main** queue's `ApproximateAgeOfOldestMessage` (and/or a composite: messages visible > 0 while worker `Invocations` == 0), and wire `var.alarm_actions` to a real SNS topic with a subscription.
- **Alternative solution:** _Composite alarm_ (queue non-empty AND worker invocations flat over N periods) — pros: matches the failure signature precisely, low false-positive rate; cons: more complex to author/test; effort M. _Simpler:_ single `ApproximateAgeOfOldestMessage` threshold on the main queue — pros: trivial, also catches generic backlogs; cons: less diagnostic specificity; effort S. Cross-pillar impact: Operational Excellence (alerting ownership / on-call), Security (shares the `alarm_actions=[]` gap).

### [High] REL-F2 — Permanent worker errors are dropped without ever reaching the DLQ or any monitored metric
- **Evidence:** `documentation/scripts/lambdas/worker-dispatcher/handler.py:88-96` — `PermanentError` is caught per-record and not re-raised; the `failed` counter is initialized but never incremented. `documentation/terraform/ingestion/main.tf:238-247` — no `ReportBatchItemFailures`, so returning normally tells SQS the whole batch succeeded and the message is deleted, never reaching the DLQ.
- **Impact:** A permanently-failing event (invalid payload, or the AccessDenied class the code explicitly treats as permanent at `handler.py:76`) is silently discarded: no DLQ entry, no `worker_errors` alarm (the invocation returns success), no feedback to the PR author. The only trace is a single log line, easy to miss. This is per-AWS-guidance the exact case partial batch responses exist to handle ([Lambda SQS batch item failures](https://docs.aws.amazon.com/lambda/latest/dg/services-sqs-errorhandling.html)).
- **Recommendation:** Either enable `ReportBatchItemFailures` and route permanent failures through the DLQ after `maxReceiveCount`, or explicitly `sqs:SendMessage` the payload to the DLQ before dropping, and/or emit a `PermanentErrors` EMF metric with its own alarm.
- **Alternative solution:** _Option A_ — EMF `PermanentErrors` metric + alarm: pros minimal change (S), no retry-storm; cons the payload itself is not preserved for replay. _Option B_ — explicit `send_message` to the DLQ on `PermanentError`: pros preserves message for inspection/redrive; cons one more IAM action + slightly more code (M). Cross-pillar impact: Operational Excellence (observability), Security (Option B is a small least-privilege addition).

### [High] REL-F3 — No blast-radius containment or safe-change mechanism for the shared worker role / in-place runtime deploy
- **Evidence:** `documentation/terraform/ingestion/main.tf:112-169` — a single `aws_iam_role.worker` + one policy serves 100% of async traffic for all repos; the inline comments at `main.tf:139-147` and `main.tf:150-165` document, in the maintainers' own words, two prior least-privilege changes that each silently halted the whole pipeline. `documentation/terraform/runtime/main.tf:11-16` — the AgentCore runtime is updated **in place** by digest, no canary/weighted rollout. Repo-wide search finds no `aws_lambda_alias`/CodeDeploy/weighted-traffic construct.
- **Impact:** Every IAM or container change is instantly 100% live with no staged rollout and no automated pre-promotion check. Combined with REL-F1 and REL-F2, an IAM/config regression can take the entire pipeline down silently for an unbounded period.
- **Recommendation:** Add an automated post-`apply` smoke test for the `ingestion` module (synthetic SQS event through the real deployed worker IAM role, assert success). Longer-term, consider staged rollout (Lambda alias + traffic shifting) for the worker.
- **Alternative solution:** _Option A_ — Lambda alias + CodeDeploy weighted shift with auto-rollback on the worker-errors alarm: pros standard blue/green; cons does not cover the poller/IAM failure mode (invisible to code-level metrics), heavy for a POC; effort L. _Option B_ — scripted post-apply smoke invocation gating "done": pros targets exactly this failure class, cheap; cons not wired into CI (none exists, cross-ref OPS); effort S–M. Cross-pillar impact: Operational Excellence (deploy-pipeline gap), Maintainability (regression coverage).

### [Medium] REL-F4 — Backoff has no jitter; one remote client relies on SDK default timeouts
- **Evidence:** `documentation/scripts/agents/agent-technical-doc/docagent/retry.py:80` — `delay = min(max_delay, base_delay * (2 ** (attempt - 1)))`, deterministic, no randomization. `documentation/scripts/lambdas/worker-dispatcher/handler.py:41-43` — `_agentcore_client()` sets no explicit `Config(connect_timeout=..., read_timeout=...)`, unlike the Bedrock analyzer client.
- **Impact:** Without jitter, concurrent retries after a shared transient failure (e.g. a Bedrock throttling burst across the up-to-5 concurrent workers) can re-synchronize and amplify load on an already-degraded dependency. The un-configured AgentCore timeout is bounded by the Lambda's own 60s timeout, but retry behavior for that path is not under explicit control.
- **Recommendation:** Add jitter to `retry_call` (e.g. `delay * random.uniform(0.5, 1.0)`) and pass explicit `botocore.config.Config` timeouts to the `bedrock-agentcore` client.
- **Alternative solution:** None — low-effort (S), low-risk, no meaningful trade-off; implement directly.
