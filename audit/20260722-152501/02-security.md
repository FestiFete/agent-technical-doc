**Independent re-verification of correctness (all confirmed on fresh read, not assumed):**
- Multi-region + global-service-events + log-file-validation are all correctly set — this is the configuration required for the trail to actually capture IAM (a global service) activity and detect tampering. Confirmed via `documentation/terraform/observability/cloudtrail.tf:144-156`.
- The S3 bucket policy (`cloudtrail.tf:65-94`) matches AWS's documented required statements (`AWSCloudTrailAclCheck` on `s3:GetBucketAcl`, `AWSCloudTrailWrite` on `s3:PutObject` scoped to `.../AWSLogs/{account_id}/*` with the `s3:x-amz-acl=bucket-owner-full-control` condition, principal `cloudtrail.amazonaws.com`) — per AWS CloudTrail docs (https://docs.aws.amazon.com/awscloudtrail/latest/userguide/create-s3-bucket-policy-for-cloudtrail.html). **One gap found on this fresh read that neither prior run could have caught (the file didn't exist yet):** AWS's own documentation explicitly recommends adding an `aws:SourceArn` condition key on both statements ("As a security best practice, add an `aws:SourceArn` condition key... Without it, any CloudTrail trail in the account (present or future, including ones created by an attacker with `cloudtrail:CreateTrail` rights) could in principle target this bucket, not just this specific trail — a narrow but real confused-deputy gap.

The IAM filter's wildcard set (`Put*Policy`, `Attach*`, `Detach*`, `Create*`, `Delete*`, `Update*`) is broad enough to catch role/user/policy creation, not just policy attachment — a reasonable, slightly conservative design given this account has no IAM users/access-key rotation traffic to generate noise. The Secrets Manager filter's non-zero threshold (30/5min, vs. the documented 1-per-webhook-delivery + 1-per-run baseline) is a sound anomaly threshold rather than a "any access" alarm, avoiding false-positive fatigue on expected traffic.

## Weaknesses / Findings

### [Low] SEC-F3 — Detective controls substantially implemented (CloudTrail + GuardDuty + IAM/Secrets alarms), but notification path unwired and Config/Security Hub still absent
- **Evidence:** `documentation/terraform/observability/cloudtrail.tf:185,217` (`alarm_actions = var.alarm_actions` on both new alarms); `documentation/terraform/observability/variables.tf:21-25` (`alarm_actions` default `[]`); repo-wide grep for `aws_sns_topic` across `documentation/terraform/` — zero matches; `documentation/terraform/shared.tfvars` and `documentation/terraform/ingestion/terraform.tfvars` — neither overrides `alarm_actions`; repo-wide grep for `aws_config|securityhub` — zero matches; `documentation/terraform/observability/cloudtrail.tf:65-94` (bucket policy present but missing the AWS-documented `aws:SourceArn` condition — https://docs.aws.amazon.com/awscloudtrail/latest/userguide/create-s3-bucket-policy-for-cloudtrail.html).
- **Impact:** CloudTrail now provides a real, tamper-evident audit trail (usable for forensics/investigation after the fact), and GuardDuty now provides automatic anomaly detection on CloudTrail management events. However, neither the two new CloudWatch alarms nor any GuardDuty finding is routed to a human or an on-call system by default — an operator would need to actively check the CloudWatch console or GuardDuty console to notice an IAM policy change, a Secrets Manager access spike, or a GuardDuty finding. This mirrors the pillar's pre-existing `OPS-F2`-style gap (the module's 3 original operational alarms have the same characteristic) rather than being a new, isolated issue. Separately, the missing `aws:SourceArn` condition on the CloudTrail bucket policy is a narrow, AWS-documented best-practice gap (confused-deputy risk: any trail in the account, not just this one, could theoretically target the bucket).
- **Recommendation:** (1) Create an SNS topic (or reuse an existing security-team channel) and set `var.alarm_actions` to include it, closing the loop for all 5 module alarms at once (the 3 operational + the 2 new security ones). (2) Add `aws:SourceArn` conditions (scoped to `aws_cloudtrail.account[0].arn`) to both statements in `data.aws_iam_policy_document.cloudtrail_bucket`. (3) Consider AWS Config (resource configuration drift/compliance) and Security Hub (finding aggregation across GuardDuty/Config/Inspector) as the next layer once the account graduates past POC scale — both are named in the SEC-10 criterion and neither is present yet.
- **Alternative solution:** (a) Wire an SNS topic + email/Slack subscription now (recommended): pros — closes the actionability gap for both the new and pre-existing alarms in one change, standard low-cost AWS pattern; cons — one more resource to manage, needs a real destination (email/chat webhook) decided outside Terraform. Effort: S. Cross-pillar impact: directly resolves part of the Operational Excellence pillar's `OPS-F2` finding as a side effect. (b) Leave alarms/GuardDuty findings console-only (current state): pros — no additional work; cons — detection without notification has materially lower real-world value — an incident could sit undetected until someone happens to check. Effort: none.

### [Low] SEC-F1 — WAF/CloudFront front in place, but the raw API Gateway origin remains directly reachable (residual bypass, unchanged)
- **Evidence:** `documentation/terraform/ingestion/waf.tf:18-21` (comment acknowledging the gap, re-confirmed present and unchanged this run); `documentation/terraform/ingestion/outputs.tf:6-8`; `documentation/terraform/ingestion/main.tf:234-269` (no resource policy/origin-verification on `aws_apigatewayv2_api.webhook`); `documentation/scripts/lambdas/webhook-receiver/handler.py:217-226` (HMAC check has no path/origin awareness, re-read this run, unchanged).
- **Impact:** Traffic sent directly to the `execute-api` URL skips AWS Managed Rules and the WAF's per-IP rate rule, though it remains bound by API Gateway's account-wide stage throttle (10 rps/20 burst, `documentation/terraform/ingestion/main.tf:257-260`) and still must pass the HMAC check before any state-changing action. No unauthenticated write path exists via either route.
- **Recommendation:** Add a shared-secret custom header (e.g. `X-Origin-Verify`) set only by the CloudFront distribution's origin custom headers and checked in the Lambda before HMAC verification.
- **Alternative solution:** (a) CloudFront custom-header origin-verification (recommended): pros — closes the bypass at negligible cost/complexity; cons — one more secret/config value to rotate and keep in sync. Effort: S. (b) Accept as residual risk (current state): pros — no work; cons — WAF's managed rules/rate limiting remain silently bypassable by anyone who discovers the `execute-api` hostname. Effort: none. Cross-pillar impact: none material.

### [Low] SEC-F2 — No customer-managed KMS keys (CMK); blocked at the account level (unchanged)
- **Evidence:** `documentation/terraform/security/main.tf:8-16,23,42`; `documentation/terraform/ingestion/main.tf:104,150`; `documentation/terraform/roles/main.tf:77-78`; `documentation/terraform/observability/cloudtrail.tf:14-16,31-39` (new CloudTrail bucket also uses `aws:kms` AWS-managed key, consistent with the existing account-wide compromise, not a new gap).
- **Impact:** Every data store, including the new CloudTrail bucket, uses AWS-managed/owned keys: no customer-controlled key policy, no configurable rotation cadence, coarser key-usage attribution.
- **Recommendation:** Request the narrow `kms:CreateKey`/key-management permissions needed, then re-enable `kms_key_id` across Secrets Manager/DynamoDB/S3/CloudTrail and enable automatic key rotation.
- **Alternative solution:** Current AWS-managed keys vs. a project CMK. Pros of CMK: key-policy control, configurable rotation, cross-account boundary, fine-grained CloudTrail key-usage logs. Cons: added operational overhead/cost, currently blocked by an org-level IAM deny outside this project's control. Effort: M (blocked on an org-level permissions change).

### [Low] SEC-F4 — Bedrock model-invoke permission scoped wider than the models actually used (unchanged)
- **Evidence:** `documentation/terraform/roles/main.tf:38-45` (`Resource = ["arn:aws:bedrock:*::foundation-model/*", "arn:aws:bedrock:*:${account_id}:inference-profile/*"]`).
- **Impact:** The runtime execution role can invoke any foundation model in any region, not just the two Claude models actually configured. No direct exploit path identified.
- **Recommendation:** Scope the `BedrockInvoke` statement's `Resource` to the specific model/inference-profile ARNs and region (`eu-central-1`) actually used.
- **Alternative solution:** None needed — straightforward tightening consistent with the existing least-privilege pattern applied elsewhere. Effort: S.

### [Low] SEC-F5 — Unpinned Python dependencies, no lockfile (unchanged)
- **Evidence:** `documentation/scripts/agents/agent-technical-doc/requirements.txt:1-8` (`bedrock-agentcore>=0.1.0`, `strands-agents[otel]>=0.1.0`, `boto3>=1.34.0`, `botocore>=1.34.0`, `pyjwt[crypto]>=2.8.0`, `aws-opentelemetry-distro>=0.10.0`); no lockfile found anywhere in the repo (`documentation/scripts/lambdas/*/requirements.txt` contain no packages — boto3 is Lambda-runtime-provided).
- **Impact:** Container builds are not reproducible and can silently pick up new — possibly vulnerable — dependency versions between builds.
- **Recommendation:** Pin exact versions (or generate a lockfile via `pip-compile`/`uv lock`) and add periodic scanning (`pip-audit`, Dependabot/Renovate).
- **Alternative solution:** None needed. Effort: S.
